AI 爬虫已经成为 git.kernel.org 持续性的资源税：它们消耗的 CPU 超过所有正常访问与 Git 克隆的总和，在五个地理分布式节点上长期占用 14 至 16 个核心，只为把 Git 提交渲染成 HTML，供模型训练者抓取。

Linux 开发史对大模型公司尤其珍贵，因为代码仓库和邮件讨论全部公开、结构清晰，并且能够保证是未经 AI 内容污染的训练语料。模型若反复学习模型生成的内容，可能发生类似"数字朊病毒"的质量退化，因此完整的内核提交历史成了高价值的 **pre-AI data**。kernel.org 已经主动提供最高效的获取方式：代码仓库可以直接 `git clone`，连整个 LKML 邮件档案也能以 Git 仓库形式下载，训练者只需克隆一次，再在本地遍历全部提交。

爬虫却选择了成本最高的路径：逐个请求网页，让服务器把每条提交实时渲染成 HTML，然后再解析页面。`linux.git` 约有 148 万条提交，git.kernel.org 上还有约 922 个共享大部分底层对象的分支；对 Git 后端而言，这些分支存储效率很高，但每个分支都会向网页爬虫暴露同一批提交，于是形成数十亿个有效 URL，让爬虫最多重复抓取 922 份相同内容。cgit 还允许请求补丁、纯文本页面以及任意提交之间的 diff，使单个仓库分支就能组合出近乎无限的昂贵 URL。这个为人类用户和遵守 `robots.txt` 的传统爬虫设计的开放界面，如今成了计算资源放大器。

管理员最初通过日志识别爬虫并用 fail2ban 封禁 IP。早期机器人会诚实声明 user-agent，随后开始伪装成普通浏览器；管理员仍可依据行为识别它们，例如某个 IP 连续遍历八年前废弃分支中的每条提交。爬虫继而分散到云服务子网，封禁整个 ASN 尚能奏效，代价只是偶尔误伤自动检查提交链接的正常云实例。

局面在爬虫转向数百万住宅和移动 IP 后恶化。每个地址只发出四五次请求便永久消失，管理员发现时攻击已经结束，封禁只会让防火墙规则无限膨胀。这些地址以集群方式突然涌入，把系统压垮后转向其他目标，等服务恢复再回来。背后的商业模式是 **proxy SDK monetization**：应用开发者把代理功能嵌入电视等家用设备，通过出售用户网络出口获利，使普通家庭设备在用户不知情时成为分布式抓取基础设施。

kernel.org 随后部署 Anubis，用工作量证明改变抓取成本。访问者必须找到一个字符串，使其与自身 IP 和服务器密钥组合后的 SHA-256 哈希具有指定数量的前导零。难度为 4 时，爬虫立即撤退，正常用户只受到轻微打扰，系统获得了几个月安宁；爬虫开始解题后，难度被提高到 5。这个级别会让手机计算数秒并明显发热，正常用户的体验进一步下降，却仍只换来几个月缓冲，因为爬虫最终也愿意支付这笔计算成本。

目前 git.kernel.org 每天收到约 600 万次查看随机提交的请求，其中 66% 在 Anubis 挑战前退出，33% 完成计算并进入主站。单凭访问记录无法绝对区分人与机器，但持续请求旧仓库随机分支里的旧提交，几乎不符合真实开发者的使用方式。即便采用一系列对爬虫有利的宽松假设，正常访问也只占总流量约 2%，其余基本都是抓取活动。

这些请求尚未让网站长期失去响应，git.kernel.org 对普通访客通常仍然迅速；更容易造成宕机的反而是设计糟糕的 CI，例如 20 个节点同时对 `stable.git` 发起 shallow clone。可爬虫已经永久吞掉五个节点合计 90 个 CPU 核心中的 14 至 16 个，平均占总容量约 20%，而实际负载以虫群式尖峰出现，风险高于一条平稳的 20% 曲线。更荒谬的是，爬虫消耗大量客户端算力破解 Anubis，再迫使服务器消耗更多算力生成本可通过一次 Git 克隆取得的数据。

kernel.org 只能逐步关闭会制造大量可抓取 URL 的功能，并限制匿名用户调用高成本操作，因此正常用户也将失去部分原有能力。开放数据本身不会被收回：任何真正需要数据的人仍可申请并下载完整副本，只是需要通过更多验证。只要定制 AI 公司继续争抢干净训练数据，应用厂商继续把家用设备变成住宅代理，单靠 IP 封禁、`robots.txt` 或工作量证明都无法解决问题；最终受损的是开放基础设施原本为人类协作提供的功能与容量。
