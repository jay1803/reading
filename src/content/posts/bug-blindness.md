软件质量问题之所以能在团队一致叫好时一路进入产品，往往是因为使用者已经学会绕开故障，却忘了自己在绕行。Dan Luu 过去以为自己每周看到数百乃至数千个 bug，是因为用电脑的方式异于常人；后来他发现，别人常常碰到同样的问题，只是没有把它们识别为问题。他受邀评估产品时，有时会发现严重到普通用户必须掌握一串违反直觉的变通办法才能使用的缺陷，而内部讨论仍称产品运转良好。产品发布后，用户遭遇他预见的障碍并弃用产品，也让他不再认为这些只是自己触发的罕见边缘情况。

这种**质量盲视**甚至能让人面对证据仍看不到缺陷。他测试 Google、Bing 和 Kagi 的搜索结果，发现一些查询返回大量 SEO 垃圾内容，甚至诈骗网站，却没有给出所需的有效答案；替 Kagi 辩护的人发来自己的结果时，结果里仍找不到及时的季节预测等目标信息。把 GitHub 固定在结果顶部能改善下载 GitHub 软件的查询，却解决不了其他查询。另一例是大学课程软件 Blackboard：它曾被广泛厌恶，2011 年一项受访者调查中有 93% 表示"讨厌"该公司，但 Luu 遇到的一名员工却以为用户很喜欢它。Discourse 员工也曾认为其论坛性能出色，尽管产品代码会延缓实际页面加载，以改善 LCP 等性能指标的表现；这类做法让指标好看，却伤害用户体验。

盲视不只来自维护自己作品的倾向，还来自**习惯性补救**。小时候，Luu 的机械鼠标因滚球积灰而移动失常，朋友几乎无法使用；他自己却能操控自如，直到观察手部动作才发现，他一直在剧烈移动鼠标来抵消指针的乱跳。后来他也养成了类似的软件习惯：新建 Google Doc 后先做别的事，再输入标题，以免立即输入的标题被覆盖；在 Microsoft 工作时，登录前先关掉笔记本 Wi‑Fi，以绕过一个联网后反而可能导致登录失败的服务检查。他认为，许多所谓电脑熟练度，正是由这种无需思考便会执行的变通动作构成的。

因此，让开发者日常使用自己的产品虽然有益，却不足以发现用户的困难：程序员尤其擅长找到绕行路径，并逐渐把它当成正常操作。用户提出障碍时，熟练者很容易回答"照这几个步骤做就行"，却没意识到初次使用的人无从猜出这些步骤。Luu 认为盲视可以改善：对于愿意接受反馈的人，持续指出他们先前没注意到的问题，几周后就可能改变其观察方式；有人多年后仍告诉他，自己如今到处都能看见 bug。他看重这种能力，是因为曾见过团队真诚相信自己交付了高质量产品，实际质量却使产品成功的机会大幅降低，甚至归零。

文章末尾的补充例子也显示，人会因自身的使用方式而漏看普遍存在的东西。许多程序员使用广告拦截器，也习惯无视现实中的广告，于是觉得广告不起作用；但 Luu 见过按地区投放与不投放的 A/B 测试，广告带来的直接收入已超过支出，还增加了用户。他并未据此断言所有广告有效，而是指出"广告普遍无效"与这些因果证据不符。同样，即使他认为 Google Docs 和 Codex 的质量高于各自领域的平均水平，仍能列出大量故障及自己形成的补救习惯。随着 coding agents 让低质量软件更容易被快速生产，也让修复性能和 bug 更容易，决定团队能否利用后一种能力的前提，仍是先看见用户正在忍受什么。
