hanako 这条帖子的核心判断是：多数人搭 agent 系统时只造了"loop"，却误以为那就是全部——loop 只能让一个工作单元本身做对，决定不了这些单元该按什么顺序、什么形状存在，这层"图"（graph）才是能不能从盯一个 agent 扩展到管一支舰队的分水岭。

她把 loop 拆成最简单的四步：产出、检查、纠正、循环直到通过。整套机制的关键在"检查"这一步——如果没有一个真的会失败的判定条件，那就不是 loop，只是一个定时器。她观察到大多数人的做法是先把活干完，再在末尾"补"一个审查（往往是另一个模型看一眼输出，本质是两个乐观主义者互相认同），而正确的顺序应该反过来：先写判定条件，写到可以被程序直接判断的地步。她特别提醒一点容易被忽略的陷阱——"没报错"不等于"做对了"，把 loop 建立在这个假设上，得到的是一个会带着干净日志、直到预算耗尽都在自信重复同一个错误的系统。

但 loop 有天花板：它只能把单个工作单元做好，管不了单元之间该怎么排布、能不能并行、有没有两步其实根本不需要互相等待。结果往往是一个agent 把每一步都执行得很精准，但整体顺序是错的、形状是错的——调 loop 本身救不了这个问题，因为问题不在 loop 里，在结构里。这正是"图"这一层开始发挥作用的地方。

图描述的是工作本身的形状：什么在跑、什么能并行、什么在等、什么根本不该跑、结果往哪流。她定义了图里的四种节点：splitter（决定怎么切工作，是最容易被低估的一步，切错了下游全白费）、worker（在独立上下文里只做一件事，避免共享上下文导致所有 worker 收敛成同一个意见）、code node（用于合并、排序、去重这类确定性操作——如果一个步骤的描述里不需要"判断/评估/总结"这类词，它就该是代码而不是 LLM）、以及 gate（验证者）。她给出一条容易被忽视的常见错误：把"然后做 X"当成一条边（edge），但如果下一步并不真的把上一步的输出当作变量来消费，那就没有边，所谓的"等待"纯粹是浪费——砍掉这些不必要的顺序依赖，往往是最大的一次性提速。核心原则是：loop 活在节点内部，图活在节点之间。

好的图有两条回路，而大多数人只造了第一条：一条是"纠正边"（短），gate 把没通过的单元打回给产出它的那一步，修的是当前这一轮；另一条是"学习边"（长），被接受的结果会作为约束反馈给 splitter，这条边才是系统会越用越聪明的原因——只有第一条边的系统跑得快，但永远不会变聪明。她给出一条关键规则：只退回失败的那个单元，不要退回整个批次，否则会连累本来做对的部分、阻碍收敛。一次退回应该随身带四样东西：失败的单元本身、判定它失败的证据、这次修改被允许的范围、以及从这次失败中提炼出的约束（供学习边使用）。

在"该不该放行"这件事上，她提出按"爆炸半径"而不是"置信度"分级：把工作按错误的可撤销成本排序——可逆且影响范围小的、可逆但影响范围大的、以及难以撤销的。难以撤销的那一类，不该设一个"置信度够高就放行"的阈值——这条车道应该始终关着，人该卡在这里，而不是审查每一个中间步骤。

落地路径她给得很具体：挑一个反复在做的流程，画出 splitter、并行车道、合并点、一个 gate、一条回边；先把 gate 建出来（要能真的大声报错），再加车道，最后才加学习边。结尾三句她当作整套方法论的浓缩：只衡量答案本身是不够的，要衡量得出答案的路径；一个不改变下一步该跑什么的"判定"只是一份报告；任何没有被转化成永久约束的失败，还会再犯一次。她的收尾判断是：大多数人会一直在调那一个 loop，然后管它叫"系统"；真正把图画出来的人，才跑得动一支舰队。

局限：这是作者本人的方法论提炼，四种节点、两条回边、爆炸半径分级等概念目前没有第三方案例或数据验证其普适性；帖子末尾附带了一个引流动作（私信关键词换取"图层"要点单页），带有内容营销性质，不影响论点本身但值得留意信源动机。
