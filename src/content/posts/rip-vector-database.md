turbopuffer 正在放弃以 ANN 向量索引组织全部数据的底层架构，让 ANN 成为普通的二级索引，从而解除多种搜索与查询执行方式对向量存储布局的依赖。这个被内部称为 **turbopuffer v3** 的新引擎将重新安排文档和索引的存储、写入、压实与查询方式；它要解决的是产品从专用向量数据库演化为通用搜索数据库后，原有物理布局造成的性能瓶颈。

早期 turbopuffer 的目标很明确：用极低成本提供足够快的向量搜索。它以 object storage 作为权威数据源，通过分层 NVMe SSD 和内存缓存获得查询性能，Cursor、Notion 等早期客户验证了这组成本与速度之间的取舍。v1 的文档只有 ID 和向量，因此让向量索引决定数据布局十分自然。当时流行的方案是基于图的向量索引，但层次聚类更适合 object storage；turbopuffer 最初采用 SPANN，随后为支持增量索引转向 SPFresh。向量先聚成簇，簇的质心继续聚类，逐层形成一棵具有单一根节点的树。

这套结构建立在键有序且唯一的 key-value 存储层上。每个簇有一个 ClusterId，簇内向量获得一个稠密的 LocalId，两者组成 **ANN address**。向量本身及其对应的文档 ID 都按这个地址存储；上层质心也采用相同机制，其 ID 指向下层簇。所谓 ANN 是主索引，具体含义就是：数据在底层的位置由它在向量聚类结构中的位置决定。

属性过滤和 BM25 全文搜索推动了 turbopuffer 从 v1 进入 v2，却没有改变这个基础。为支持高效、高召回率的向量过滤，属性倒排索引将属性值映射到符合条件的文档的 ANN address；为在查询结果中返回属性，文档属性也与 ID、向量一起存放在该地址下。全文索引同样以 ANN address 标识命中文档，并在 postings 中附带词频与文档长度，供 BM25 评分。之后增加的聚合、regex search、fuzzy matching、sparse vector search 和属性排序，也全部建立在这套以向量为中心的存储布局之上。

这套架构长期保留，是因为它在 object storage 上的 ANN 搜索表现极好：单个索引已能容纳超过 100 billion 个向量，在每秒超过 1,000 次查询的负载下，实现 200 ms 的 p99 读取延迟。更改布局会冒着损害这项核心能力的风险。但随着查询类型扩展，继续围绕 ANN address 组织所有数据，开始在存储放大、写入放大和查询执行的批处理效率上付出越来越高的代价。

存储放大首先暴露了文档与向量绑定过紧的问题。只有一个向量时，文档的非向量内容只需跟随它存储一次；当 document nesting 或 late interaction 等表示方式要求一个文档包含多个向量时，同一份文档内容就需要为每个向量重复存储。这也是 turbopuffer 对每个 namespace 的向量列数量设置限制的原因之一：向量数量的增长会连带放大本不需要重复的文档数据。

写入放大则来自聚类维护与文档位置之间的联动。插入、更新或删除文档时，SPFresh 可能重新平衡向量，以维持聚类质量和搜索召回率；一旦向量换了 ANN address，以这个地址为键的完整文档内容就必须搬迁，引用旧地址的属性倒排索引和全文索引也要随之更新。更新一个向量，可能导致数百个属性及其索引一起移动。这种放大已使索引写入吞吐量的优化逐渐遭遇收益递减。

更深的限制是，不同查询需要不同的处理块大小，ANN 主索引却把它们锁在了向量聚类的尺度上。现代查询引擎通过 **vectorized execution**，在紧凑循环中批量处理一组值，以摊薄每块固定开销、提高压缩率、保持 CPU 流水线忙碌并利用 SIMD；这里的“向量化执行”指批处理计算。DuckDB 通常每批处理 2,048 行，ClickHouse 可达约 65,000 行，Lucene 的 postings block 包含 256 个文档，而 turbopuffer 的 ANN 索引最适合每簇约 100—200 个文档。聚合或扫描即使需要数千条记录才能充分利用 CPU，也会被文档按簇分块的布局限制在 100—200 条。

全文搜索的改进已经证明，摆脱这种物理边界能带来巨大收益。早期全文索引按 ANN 簇边界切分 posting lists，每块 postings 数量的中位数仅约 1.5；FTS v2 改用每块约 256 条的固定分块后，索引缩小到原来的十分之一，查询最高加速 20 倍。posting lists 能这样重排，是因为它们独立存储，只需保留指向文档的引用；聚合与其他扫描必须读取文档本体，而文档仍然每个簇存一块，因此无法获得同样的布局自由。

v3 的核心改动就是不再以 ANN address 为数据主键，让文档的存储位置脱离向量聚类结构，ANN 降为二级索引。这个方向同时针对三类瓶颈：多向量表示不再要求完整文档随每个向量重复，聚类调整不再牵动全部文档内容与引用索引，不同查询也能采用更适合自己的数据块布局。不过，文章尚未公布新主索引的具体设计，也没有证明这些目标已经转化为生产性能收益。

截至 2026 年 9 月初，v3 已通过全部 CI 检查，但性能相较生产版本仍有显著退步；团队此前优先完成基础设计与正确性验证，性能调优才刚开始，后续将逐步公开架构变化和 benchmark。彼时 turbopuffer 已承载超过 1 trillion 个文档，每秒处理超过 10 million 次写入和 25,000 次查询。此次重构的核心判断是：当数据库承担越来越多查询类型时，让一种查询的最优索引决定所有数据的物理组织，会把最初的专用优势变成整个系统的扩展边界。
