AI 能把工程师的代码产出放大一个数量级，但兑现这种增益需要重组整个工程流程，随之产生的新瓶颈则集中在人类的注意力、判断力和团队共享上下文上。Neil Kakkar 从 Bloomberg、PostHog 到 AI-native 创业公司 Tano 的经历，呈现了这场转变的具体机制：写代码越来越便宜，协调、审核、决定做什么以及承担错误后果，开始决定组织能跑多快。

Neil 在 Bloomberg 工作三年，在 PostHog 工作约四年，加入 Tano 后担任首位工程师，文章主要比较他在 PostHog 的 45 个月与 Tano 的八个月。Bloomberg 有约两万名员工；PostHog 从他加入时约十人增长到约两百人；Tano 则从创立发展到约十人。他在 PostHog 每月合并的 PR 数量是 Bloomberg 时期的 2.4 倍，到 Tano 又提高到 PostHog 的 11 倍，从每月约 8—20 个增加到 200 多个，每月代码量超过十万行。PostHog 的比较数据来自 AI 普及之前，如今该公司也已积极采用 AI。这组个人经历同时包含资历增长、公司规模与文化差异，无法把全部增幅归因于工具；PR 数量也不能直接证明产品价值，但具体工作范围说明，增量包含了实质性的产品开发和系统改造。

在 PostHog，Neil 做过数据摄取、ClickHouse 上的漏斗与留存查询优化、十亿级事件处理，并从零构建 experimentation 产品，后来负责 surveys、early access features 和 feature flags。在 Tano，他把相近广度的工作压缩进八个月，建设 affiliate platform、优化内容监测系统，并把整个 agent 架构迁移到具备 persistent memory、更好工具和 observability 的新系统。他使用 Claude Code Desktop，通常同时推进三到五件事：先讨论方案，让 agent 完成开发、审核、验证与截图，处理评论并准备 PR，再通过每个 PR 附带的 HTML 说明检查实现。一个完整任务常运行一到两小时，复杂研究更久；临时 bug 和小需求也可以交给独立工作线程处理，减少对主任务的直接打断。

工具带来的并行能力只有在组织解除下游约束后，才能转化为交付速度。Neil 设想，若带着今天的 AI 回到强制人工审核的旧 PostHog，个人生产率大概只能提高一到两倍：自己的代码写得再快，同事也没有更多时间审核，PR 会积压在审批队列里。Tano 因而尽量让一名工程师端到端负责完整功能，只对影响整个产品的架构决策集中讨论，其他事项依靠信任和主动披露风险推进。PostHog 当年做 surveys V1，需要两名工程师和一名设计师协作一个月，前后端修改经常互相牵动；在 agent 能覆盖整个技术栈后，职责完整且结果明确的功能交给一个人，可以省掉大量交接。讨论未知问题仍然有价值，但明确任务的分工收益已经发生变化。

同样的调整发生在 code review。Tano 的新工程师仍需人工审核，熟悉代码库、审核意见逐渐减少后可以自行合并；Neil 用了三周，其他人可能需要八周。每个 PR 都会经过基于 Claude Code GitHub Actions 的自动审核，高风险改动可以额外调用更强的 agent，成熟工程师的大多数 PR 不再接受人工审核。由此，PR 合并时间的中位数降到一小时以内。Tano 的回滚率比 PostHog 低六倍，但这一指标受到处置习惯影响：他们更常直接修复线上问题，而非回滚，因此低回滚率不能等同于低故障率；Neil 同时认为，模型进步与自动审核也在减少代码错误。

这种速度以明确接受部分生产事故为前提。一次财务报表更新中，agent 把货币最小单位统一按 100 换算，遗漏了 Bahraini dinar 的一 dinar 对应 1,000 fulūs，也没有复用代码库已有的货币计算工具；部署后报表数字出现偏差，团队在一小时内修复。另一次，他们给约 25 GB、六百万行的 Postgres posts 表添加 partial index，阻塞式 migration 导致写入停滞、内容摄取中断，migration 超时又让后续部署失败。此后团队要求此类索引并发创建，并把大表清单和禁止阻塞迁移的规则写进审核 agent。每次新故障都要变成后续自动审核的具体约束，快速修复能力则支撑了他们接受风险的选择。

交付流程加速后，工程师还必须自己承担更多产品判断。Bloomberg 的每个工程团队有专职 product manager，Neil 基本不直接接触客户；PostHog 由一名 product manager 支持多个团队，同时要求工程师访谈客户、研究需求并形成产品意见；Tano 没有 product manager。每周一，工程师提出遇到的问题和潜在风险，CEO 与 CTO 补充客户流失风险、成交所需功能等商业背景，团队共同排序，再由工程师分别负责实施。例如，每位客户带来的 support tickets 持续增加，就意味着现有人工支持方式无法随客户规模扩张。过去一个月的工作如今经常一周完成，背后同时有 agent 加速、多项目并行和减少需求交接三项变化。

更深远的变化是，架构决策开始更容易撤销。PostHog 的 person-on-events migration 持续一年：原先处理漏斗和独立用户查询时，需要把二百多亿条事件与 persons 表连接，再按人聚合，大客户的查询因此慢到难以使用；迁移把 person identifier 和 properties 放进事件，要求全公司手工修改相关查询。因为再次迁移代价过高，团队必须提前考虑长期需求。Tano 则在数周内完成复杂架构迁移：其 AI agents 负责与 creators 沟通、谈判、审核内容并交给品牌批准，早期自由清单式架构容易选错工具且缺乏 observability，团队先迁移到任务明确、工具集合受限的 workflow，随后再次迁移，补足同一 creator 多条沟通线程之间的上下文。第二次迁移遗漏防护，甚至造成重复付款，但团队仍选择承担代价，以尽快获得可扩展的新架构。改造成本下降后，先在生产中取得信息、再快速修正，成为他们能够采用的策略；这也扩大了产品实验和客户定制的空间。

这些收益把瓶颈推向了 Neil 本人。三到五条工作流不断生成 PR，需要他维持更多上下文、审阅更多结果，工作日结束时比过去更疲惫。尤其当一个 bug 只需启动 Claude、一小时内便能解决时，随手开新任务的诱惑非常强；每件事单独看都便宜，累积起来却持续挤占本周最重要的目标。他用 **thrashing** 描述这种状态：系统把过多时间花在任务切换上，整体有效产出受损。限制并发、优先完成最高价值任务，因而成为 AI 工作流中的关键能力；任务容易执行，并不足以成为立刻执行的理由。

取消人工审核还削弱了团队的共享知识。Neil 在 PostHog 曾阅读所有 PR，借此了解同事正在做什么，发现重复实现并提供帮助；随着公司从约二十人增长到一百人，每个工作日的 PR 从十五个增加到三十个，这种做法已无法持续。如今约十人的 Tano 每天同样合并约三十个 PR，他几乎不再审核资深同事的代码。独立负责大块产品让每个人更快，也让上下文更容易只存在于一个人的脑中，协作减少，**bus factor** 风险加剧。他提出把产品领域知识持续记录进 AGENTS.md，让后来者通过 AI 学习和接手，但这仍是需要主动维护的补偿机制。

个人节奏也必须重新设计。过去写代码的速度天然限制了一天能推进多少事情，下午提交 PR、等待审核也形成间歇；现在 agents 全天产出，工程师随时都能启动更多工作。Neil 刚加入 Tano 时把任务集中在早上并行展开，下午三点便精疲力竭，晚间再做重要修改更容易漏掉问题。他后来固定下午六点结束工作，把笔记本留在办公室，让本地 agents 再运行一两个小时，第二天处理结果；上午九点到十一点发起的 PR 占比从 PostHog 时的 9% 增加到 Tano 的 18%。这一安排既利用异步执行，也建立明确的下班边界，缓解“AI 还可以继续工作，自己却在休息”的压力。他也开始筛选个人项目，优先做一直想尝试的 AI 动画频道，放下同时开发音乐生成器、视频编辑器等多个应用的冲动。

产量提升还可能掩盖设计与品牌投入的不足。PostHog 的前十名员工中就有一位艺术家和一位设计师，共同塑造了鲜明品牌；Tano 使用 AI 生成的 neo-brutalist 设计，最终看起来与现成组件库十分接近，需要重新明确品牌方向。工具能低成本生成“看起来不错”的界面，却也让初创团队更容易接受同质化结果。与此同时，算力预算依然构成实际约束：Tano 每人只有一份 20x Claude Max 订阅，Neil 的用量若按 API 价格计费，每月会超过 8,000 美元。尝试让 agents 自主循环、检查日志和修错时尤其容易触及额度，限制迫使他重新排序任务。他希望进一步测试 agent 能否持续检查日志、session recordings 和 creator 对话，主动发现重复付款等问题，但这些自主监测能力仍是待验证的方向。

Neil 最终把 AI 视为速度乘数，把允许实验、承认错误并持续解除约束的文化视为实现增益的条件。约束会连续迁移：他引用 Anthropic 的经历，自动化 code review 后，CI 成为瓶颈；扩展 CI 后，source control 又跟不上，需要重新设计。一个组织若只提高代码生成速度，保留原有审核、交接和基础设施容量，新增工作就会堵在下一环。Tano 的经验说明，全公司共同调整流程可以放大收益；它尚不能证明同一套风险取舍适合所有业务。

Gergely Orosz 补充的边界尤其重要：行业平均 PR 增幅约为两倍，Neil 的十一倍同时反映了 AI 使用与进入更年轻公司的差异。已有成熟业务的公司需要保护客户和收入，改变流程必须更谨慎；年轻的 AI-native 公司拥有更大的试错空间，可能因此获得暂时的迭代优势。但迭代速度只有连接到 product-market fit、收入和健康的 unit economics 才有意义。随着代码生产越来越便宜，工程组织的竞争重心转向了选择值得做的事、控制试错后果，以及保护持续作出可靠判断的人。
