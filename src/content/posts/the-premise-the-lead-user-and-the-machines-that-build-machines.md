## TL;DR
Feld 的真正判断不是“AI 会让编程更快”，而是“终端用户的软件创新会全部从用户侧发生，因为用户掌握需求现场的 sticky information，而机器会承担制造商职能”。这把 von Hippel 的 Lead User 理论推进到 AI 软件时代：用户不再只是先行需求者，也不必再跨越成为厂商的组织门槛，提示词和自动化机器让“用户-制造商”边界开始消失。

## 核心主张拆解
### Lead User 理论的延伸
Eric von Hippel 1978 年提出“创新来自用户，而不是制造商”，当时反主流，因为传统产品模型默认制造商提出想法、用户接收产品。Lead users 的特征是比市场更早遇到需求，并在货架上没有解决方案时自己动手构建。

Feld 把这个框架迁移到 end-user software：如果想知道软件品类会往哪里走，应观察最早被真实需求卡住、已经在拼装解决方案的人，而不是只看厂商路线图。

### sticky information 是关键变量
文章最重要的理论支点是 sticky information：解决问题所需的信息很难被搬运，它通常停留在需求发生处，也就是用户那里。AI 机器的意义在于降低“把需求现场的信息转译成可运行软件”的成本，因此创新地点更自然地留在用户侧。

### 机器成为用户操作的制造商
Feld 的新增命题是：未来 end-user software innovation 不只是由用户发现或发起，而是应由机器以高度自动化方式构建、测试、交付。用户拥有需求和上下文，机器拥有制造能力，二者之间的接口可能只是一段提示词或一套自动化流程。

## 例子与方法
FOSS 是 von Hippel 框架的经典例子：需要软件的人自己写软件，用户与制造商合并为同一人。Feld 认为 AI 进一步降低这个合并门槛，因为用户可以不再亲自写完整代码，而是驱动“机器制造软件”。

他用自己早前做的小插件作为 First User 案例：不是为了销售或产品化，而是因为自己需要。用户是他，制造商是机器，边界是一段 prompt。

他也借用 Dan Shapiro 关于 Software Factory / Dark Factory 的分层讨论，但选择用“machine”而不是“agent”描述自己的系统：machine 必须有清晰输入、输出和工作定义，避免 agent 一词被泛化后失去约束力。

## 值得质疑
“所有未来终端用户软件创新都来自用户”这个说法有意极端，文章没有证明所有场景都会如此。平台级基础设施、监管密集软件、复杂协作型企业系统仍可能需要传统厂商承担集成、责任、分发和长期维护。

更实际的版本可能是：需求发现和原型创新会强烈向用户侧迁移，厂商价值从“猜需求并制造产品”转向“提供可靠机器、约束系统、分发渠道、治理和规模化维护”。

## 收束
这篇文章的方向感很强：AI 编程的核心变化不是工程师效率工具，而是创新权力从产品组织继续下沉到拥有真实需求的用户手里；真正要观察的，不是哪个 agent 名词流行，而是哪类用户开始拥有自己的软件工厂。
