# BEGIN_OPENCLAW_SUMMARY
## TL;DR
给推荐链接强行追加 referral query string，问题不只在于“像追踪参数”让人不舒服；更严重的是它实际改变了 URL 的身份：一个原本可用、由站点作者定义的资源地址，会变成另一个可能 404、可能语义不同、且未经用户同意的地址。

## 核心主张拆解
- Susam Pal 原本在 Wander Console 0.4.0 加入 `via=` 参数，让被推荐网站的服务器日志能看到访问来自哪个 Wander console。这满足了社区里“知道流量来源”的需求，也有 opt-out，但默认行为仍然会改写外站 URL。
- Chris Morgan 的批评点击中了作者没有说清的直觉：若站点作者想知道来源，应依赖 Referer；若浏览器没带 Referer，往往有隐私或策略原因。把来源塞进目标 URL，是工具替用户和目标站点做了额外决定。
- 作者最终发现风险并非抽象伦理：`https://int10h.org/oldschool-pc-fonts/fontlist/` 正常可访问，但加上任意 query string 后返回 404。所谓“只加一个参数”已经生成了新 URL，不再是原链接。
- 这使 referral query 从“方便统计的小功能”变成破坏 Web 契约的 misfeature：链接应按推荐者拿到的原样打开，工具不该为了可观测性改写资源标识符。

## 背后的产品教训
- 这个错误来自典型的低能量决策：作者忙于代数图论研究，只在休息间隙维护 Wander Console；他对需求有抵触，却没留出时间把抵触转成明确原则，于是用“有人要 + 可以 opt out”压过了设计判断。
- 对小型个人项目，克制比功能响应更重要。作者本来偏好功能稳定、范围有限，但在疲劳状态下接受了一个违背项目精神的改动。
- 默认值比选项更关键。即使提供禁用开关，只要默认会改写别人的 URL，破坏和道德负担已经发生在用户看不见的路径上。

## 值得质疑
- 文章对 Referer 的替代性说得偏快：现代浏览器和站点策略经常限制 Referer，日志统计需求确实可能存在。但这只能说明“来源可见性有需求”，不能推出“可以改写目标 URL”。
- 更稳的设计可能是 console 侧自留统计、显式跳转页、或让被推荐站点自愿加入协议；这些方案都比把参数塞进外部 URL 更尊重边界。

## 最后一层
这篇文章真正有价值的地方，是把“不要加追踪参数”落到 URL 语义本身：URL 不是可随手装饰的显示文本，而是资源身份；一旦工具替用户改写它，就已经越过了链接与跟踪之间的边界。
