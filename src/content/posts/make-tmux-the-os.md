桌面操作系统应该把"任务"变成组织工作的基本单位，让窗口、浏览器标签页和应用内信息获得类似 tmux 的持久会话、可滚动画布与随时恢复能力，同时让普通用户无需配置文件就能使用。Mat Duggan 设想的"tmux is the OS"，要解决的是传统窗口管理与真实工作方式之间的错位：屏幕配置每天反复变化，一个任务横跨多个应用，相关资料散落在浏览器、聊天工具和应用数据库里，操作系统却仍把它们当成互不相关的窗口和文件。

这种错位在多显示器环境中尤其明显。Duggan 每天大约六次在笔记本屏幕和桌面显示器之间切换，拔掉扩展坞就得重新拖动、缩放窗口。双屏也不等于一块连续的大屏：人们往往用主屏处理终端、代码和浏览器，用副屏放待办、聊天和邮件，偶尔瞥一眼。Grudin 在 2001 年就记录过这种"焦点工作与外围信息"的分工，操作系统至今仍不理解两块屏幕的不同角色。2004 年的窗口管理研究也已区分出三类用户：把窗口最大化后切换的人、主窗口旁保留少量辅助窗口的人，以及精心排列多个窗口的人；同一研究还记录了公开内容与私人内容的区分。桌面设计需要同时容纳这些习惯，并处理接入投影仪时私人窗口意外曝光的问题。

浏览器和文件系统进一步暴露了旧模型的局限。写 Terraform 时，Vim 中的代码、provider 文档标签页和工单更新属于同一条工作流，浏览器却把标签页关在自己的应用边界里；同一个文档标签页又可能服务于写代码和更新工单两个任务，强制归入单一分组会制造新的管理负担。与此同时，Apple Notes、iMessage、Teams 和 Slack 中的内容分别属于各自的存储系统，在 Firefox 中打开的 PDF 也未必已经保存为本地文件。Windows 95、System 7 时代那条"生成文件、用应用打开、保存、发送"的工作链，依赖操作系统能看见文件的位置，如今已无法覆盖大量日常信息。用户需要跨应用查看和检索最近接触过的资料，包括邮件与聊天内容，而不用先把它们导出成副本。

围绕任务组织桌面已有数十年的研究积累。1986 年 Henderson 和 Card 提出的 Rooms，把屏幕比作内存，把暂时关闭的窗口比作换出到磁盘的页面：窗口通常以两到十个为一组被共同使用，这个工作集对应一个任务。论文借用了程序局部性的解释——程序约 98% 的时间停留在工作集内，约一半运行成本却发生在其余 2% 的切换过程中——主张提前恢复下一组工作环境，减少用户重新找回上下文的"knowledge faulting"。2005 年关于碎片化工作的研究则发现，人们一天会在大约十个"working spheres"之间来回切换，每次往往只有几分钟，长期专注于单一任务并非普遍的工作状态。

WindowScape 提供了更灵活的思路：每次窗口排列变化就拍下快照，用户通过快照返回工作场景，无需事先决定新窗口属于哪个容器。同一个窗口可以出现在多张快照中，底层仍只有一个对象，这也解释了共享浏览器标签页如何服务于不同任务。Duggan 最初认为这些快照会消失是需要补上的缺口，希望工作场景能够长期保存；后来的实验却让他意识到，消失本身承担着清理旧状态的作用。

现有产品分别解决了部分问题，却没有形成普通用户默认可用的整体。平铺窗口管理器减少了手动排布，但教程动辄要求修改配置文件甚至克隆仓库，使用门槛过高；Niri 已实现可水平滚动的平铺布局，让用户把一组窗口留在原处，再滚到另一侧继续工作，空间机制相当接近他的设想。Arc 和 Chrome OS 则把浏览器发展成更完整的操作系统。Duggan 主张让独立承担工作的 Web 应用拥有独立窗口，让辅助查阅资料的浏览器窗口保留多个标签页，并与相关本地应用一起归入任务，使 Web 内容获得操作系统层面的身份。

Windows Timeline、Windows Sets、macOS Stage Manager、KDE Activities 和 PWA 安装机制，也都触及过这条路线。Timeline 依赖应用主动上报活动，参与不足，全面记录又引发监控感，界面还夹带用户不需要的 Edge 推广；2018 至 2019 年间被取消的 Sets，曾把应用和网页放进共享标签组，是最接近跨应用任务容器的尝试。Stage Manager 偏向 iPad 式的单应用快速切换，难以满足桌面上两三个工具协同工作的需求；KDE Activities 已支持任务范围内的桌面状态，但需要用户手动配置，最需要帮助的人往往不会启用。Duggan 据此判断，任务组织必须成为操作系统可见所有应用的基础结构，并且默认生效，否则仍会被分发、兼容性和配置成本挡住。

他提出的空间结构是**一张无限画布，每块物理显示器都是观察它的视口**。切换显示器时，窗口的水平顺序、滚动位置、输入焦点和任务归属保持不变，列宽按确定性规则重新排布，放不下的内容进入可滚动区域。双屏分别对准主任务和辅助信息区域；拔掉扩展坞只会撤去第二个视口，原来的内容仍可滚动抵达，重新接入后则恢复此前的观察位置。系统可根据输入焦点记录推断显示器角色：接收约 90% 键盘输入的屏幕承担主要工作，长期可见却很少获得焦点的窗口属于 glanceables。小屏幕下，这些辅助窗口收缩成窄条。同一底层结构也能覆盖三类用户：一列全宽、多一条辅助栏，或者多列协作，无需强迫所有人采用同一种布局。

隐私保护则必须由明确的系统状态触发。Duggan 最初想把私人窗口放在画布左侧、公开窗口放在右侧，并在用户闲置时自动滚回公开区域，但试用立即暴露了错误：阅读时没有输入，系统会把正在看的内容移走；宽屏上的私人内容即使偏在左侧，路人仍然能看见。修正后的设计把"私人"设为窗口或标签页的属性，根据已连接显示器、正在进行的屏幕捕获等机器可观测事实决定遮挡，放弃从闲置推断人的注意力或现场风险。接入陌生显示器时，默认只显示"准备演示"界面，由用户明确选择展示任务、窗口或扩展画布；屏幕共享遵循同样规则，已知显示器则恢复既有设置。这相当于把 Keynote 已使用二十多年的演讲者视图提升为桌面基础能力，让默认行为承担防泄漏责任。

本地 LLM 的用途，是降低建立任务和组织窗口的成本。用户通过全局快捷键唤出类似 Quake 下拉终端的"Ask"输入框，用自然语言描述需求；模型经由动词集合受限的 MCP server 查询窗口和标签页内容，提出分组、布局方案并展示预览，用户确认后才执行。模型不直接操作窗口管理器。这里的经济性来自工作模式的重复：设计师反复打开网络文件、修改、保存、贴进聊天，工程师反复查工单、写代码、更新状态、开 PR；笔记本、办公桌、会议室也只是有限几种显示环境。昂贵的分类、提案和确认只需在新情境出现时运行，日常操作依靠**确定性重放**，复杂 JSON 可以留给模型处理，配置文件无需再充当人的交互界面。

自动整理仍必须服从用户的空间记忆。Kirsh 和 Maglio 关于 epistemic action 的研究指出，Tetris 玩家旋转方块的次数超过完成游戏动作本身所需，因为旋转也是理解方块的思考过程；窗口排列同样承载正在进行的思考，助手中途"优化"布局会打断它。Duggan 因而倾向于"追加、不替换"，保留既有布局，让新内容向外扩展。由于 LLM 在"可以碰这些、绝不能碰那些"上并不可靠，约束应由确定性执行器实施：模型只能提案，执行器拒绝修改任何已固定的对象。任务由此成为类似目录的高层入口，将聊天窗口、浏览器、Preview 等共同组织起来，用户可以从工作目的进入资料与工具。

Linux VM 中的尝试也揭示了这套设计尚未解决的矛盾。判断主副屏、识别辅助窗口、理解任务关系，都需要持续观察行为；即使数据只在本地短暂保存，一个强调隐私的窗口管理器仍会收集比现有系统更多的活动信息。无限画布与只追加规则则让杂乱持续积累：空间记忆得到保护，旧任务却没有退出机制，桌面很快变得令人难以应付。WindowScape 会消失的快照原来相当于垃圾回收，而让内容休眠又会触及"不得扰动旧状态"的承诺。Duggan 尚未做出可运行的完整演示，只有全局下拉输入框、滚动平铺等部分机制初步可用。这个实验留下的核心问题因此超出了窗口如何摆放：任务型桌面必须同时解释工作如何恢复、隐私如何被强制保护，以及旧上下文如何在不破坏记忆的前提下退出。
