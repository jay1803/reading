Agentic engineering 的生产力上限，取决于工程师能否让多个 agent 独立完成执行与验证，并把自己的注意力留给任务分配、结果判断和产品品味。Jacob Bartlett 在一年多的日常实践中形成的核心判断是：使用 agent 本身就是一种需要训练的技能，关键在于分清它们擅长与不擅长的工作、启动能够长时间自主运行的任务，以及判断什么才是好的软件。随着多个 agent 同时工作，开发者的工作节奏也从持续沉浸于一段代码，转向不断切换、协调几条并行任务。

要维持这种并行，首先得解决工作上下文的找回问题。Claude 的 `--resume` 和 Codex 的 `resume` 能恢复会话，但使用者通常仍需记住原来的目录；多个 checkout、git worktree 和临时会话混在一起时，连当时用了哪个 agent 都可能忘记。Bartlett 为此建立了自动更新的**会话台账**，记录每次会话的工作目录、对话记录和 resume ID，再让 agent 对台账做语义搜索。只需描述"找到之前执行 review-pass 的那次会话"，系统便能返回切换到准确目录并恢复指定会话的完整命令。这样，过去的调查与实现过程就能按任务含义检索，无须依靠人记住终端和目录的位置。

找回上下文减少了重新开始的成本，**自动验证**则决定了任务能在多大程度上脱离人的持续照看。Bartlett 把构建并运行代码、对照设计检查界面、执行单元测试视为 agent 工作的基础能力。前沿模型执行计划、写出代码可能只需五分钟，完成整个页面可能需要十分钟；加入自检与修正后，一次自主工作可以延长到二十分钟、一小时，甚至整夜。并行的前提是每条任务都能自行检查结果，否则人会成为所有任务共同等待的验收瓶颈。因此，他会主动尝试把更多验证工作交出去，为 agent 配齐执行和检查所需的工具，再启动下一项任务。

验证结果还需要被整理成人能快速审阅的证据。Bartlett 常让 agent 为全部改动截图，汇总到本地 HTML 页面；涉及设计还原时，把 Figma 设计与实现左右并排，或提供滑块直接比较修改前后；涉及动画时录制屏幕，涉及复杂机制时生成 Excalidraw 图。代码层面，他会要求 Sol 完工后启动 Fable 做 review，或反过来安排，再修复其中有实质价值的问题。他特意排除"无谓的防御性代码"：agent 总能找出一批所谓问题，照单全收容易增加代码膨胀，交叉审查仍需明确质量标准。

这种证据驱动的审阅方式也可以扩展到完整产品的打磨。在赌场风格的饮酒记录应用 The Damage 发布前，Bartlett 让 agent 建立覆盖每个页面的界面图册，放到一个小型本地服务器上，每页配一个反馈文本框。他逐页填写视觉修改意见，系统把反馈自动关联到对应界面，再交给 Sol-xhigh 通宵处理；第一轮执行了五小时，完成面向 App Review 的修改准备。人工注意力因此集中到具体界面的判断与反馈，截图收集、问题定位和修改执行则由 agent 串联起来。他描述的工作状态是，下午三点左右已有约十个终端标签页同时自主运行，自己甚至不必逐一打开应用完成检查。

所提供的正文在复杂问题协作章节的 "The Fast Lane" 开头进入付费截断，尚未展开 ARGUMENT.md、设计探索、陌生技术领域和个人软件等后续方法。可见部分已经支撑一个明确结论：让更多 agent 同时写代码，只增加了执行端的数量；让每个 agent 都能恢复上下文、自行验证，并提交可快速审阅的证据，才让人的判断能力能够支撑更多并行工作。
