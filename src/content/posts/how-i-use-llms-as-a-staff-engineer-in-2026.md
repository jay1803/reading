## TL;DR
2026 年最重要的工程 AI 技能，不是会不会用 agent，而是能否把尽可能多的小型、低风险、可审查工作转移给 agent，同时保留人类判断在任务筛选、验收、沟通和复杂调试中的控制权。

## 核心洞见
作者的实际变化很激进：一年前他主要把 LLM 当 autocomplete、问答工具、一次性研究代码生成器和少量 bugfix 尝试；现在他几乎每个代码改动都会先让 agent 做一版，通常只做一次编辑 pass 后就推 PR。

这个转变来自 agent 的可靠性跃迁。早期 agent 需要边跑边盯、及时纠偏；2026 年的 agent 速度更快，也更常能自我恢复，所以人的工作从“过程监工”变成“结果筛选 + 深度审查”。他经常在 30 秒内拒掉一个 agent 方案；困难任务可能连续拒绝五六版，直到出现值得接手的版本。

## 具体机制
Bug 调查是作者最依赖 agent 的场景。他现在会把几乎每个 bug 都扔给新 agent session，因为 agent 大约能独立诊断 80% 的问题，尤其适合跨多个 repo 追线索。复杂 bug 仍需要人类专家缩小搜索空间：补日志、补 Slack 背景、搭 reproduction、指出错误假设，再重启或提示 agent。作者举的例子里，第 14 个 agent 才找到 bug，但他仍把发现归因于自己，因为前 13 次和人工分析已经把问题压缩到 agent 可解的形状。

测试和本机环境排障也被外包得更多。过去他会让 LLM 生成 curl 测试脚本；现在直接让 agent 测改动，再读它的执行日志。单元测试和集成测试因为生成成本下降而变得更“便宜”，但生产代码仍必须严格审查。他也会让 agent 处理 nvm 版本错乱这类本机 config 问题，把它当作更快的 Google 替代品。

## 边界没有消失
作者仍坚持自己写 PR 描述、Slack、ADR、issue 和博客正文。理由不是 LLM 不能写，而是这些文本承载判断、责任和人类在场信号；让 LLM 代写会弱化“我已经理解并承担这个改动”的可信度。

他也不让 agent 测 UI，因为 UI 细节依赖细微观感；不接受未审查代码；不把 sweeping changes 交给 agent 后直接信任。AI 的使用半径扩大了，但风险边界仍由代码审查、任务风险和沟通责任决定。

## 值得质疑
“80% bug 可独立诊断”高度依赖作者所在代码库、工具链、agent 能访问的上下文，以及 bug 类型；这个数字不应直接外推到安全关键、硬件、分布式一致性或强领域知识系统。文章也默认人类 reviewer 有足够能力快速识别 agent 方案是否偏航，但这正是许多团队最缺的能力。

更大的风险是组织层面：当“说 yes 的成本”下降，工程师可能接下更多低风险小事，短期 throughput 上升，但长期可能增加 review 负债、测试膨胀和架构噪音。agent 让小改动更便宜，不等于所有小改动都值得做。

## 最后一层
这篇文章真正描述的是 staff engineer 的工作重心迁移：从亲手写每一段实现，转向设计任务边界、批量启动尝试、快速淘汰坏解、保留沟通责任，并在关键处用人类判断兜底。agent 越强，人的价值越集中在“知道什么可以交出去，以及什么时候必须收回来”。
