## TL;DR
未来软件不是“UI 死亡”，而是产品入口从人类点击迁移到代理调用：真正的竞争点会从界面易用性扩展到“代理是否能被教会、被观测、被纠错、被补足上下文”。

## 核心主张拆解
- Salesforce 推出 Headless 360，把 CRM 能力暴露为 API、MCP 工具和 CLI，是老牌企业软件承认“代理入口”会侵蚀传统 UI 护城河的标志；Ramp 自身 MCP 周活跃用户三个月增长 10 倍，说明这个入口迁移已经在真实业务里发生。
- 作者不认为 UI 会消失：人仍需要查看配置、确认结果、处理例外。但交互主流会从“用户 → 界面 → 数据库”变成“用户 → 用户代理 → 软件代理 → 数据库”，UI 从主要操作面变成确认、解释与兜底层。
- 产品团队的新对象不只是人类用户，而是代表用户行动的代理。代理不会像人一样探索界面、容忍模糊文案、自己补 API 细节；它需要明确规范、上下文提示、可调用能力和失败反馈路径。

## 具体机制
- **把隐性产品知识交给代理。** Notion MCP 的关键不是“有接口”，而是在工具描述里强制代理先读取 enhanced markdown spec；这等于把过去写给开发者的 API 文档，改造成代理调用前的即时操作规范。Slack MCP 的反例是：代理默认使用通用 Markdown，结果和 Slack 私有格式冲突，用户被迫返工。
- **为代理调用建立可观测性。** Ramp 看不到用户聊天上下文，只看工具调用量无法判断需求和失败点，于是要求每次调用携带 rationale 参数，用“调用理由”重建用户意图；再提供反馈工具，让卡住的代理提交目标、尝试路径和阻塞原因。
- **把代理反馈转成产品路线图。** 如果理由日志反复出现“生成事故报告”，这不是单个工具调用优化，而是新产品能力信号；上线 build-incident-report 后，代理反馈“拉入了三天前无关工单”或“错误包含免费层用户”，就能转化为日期范围、客户层级过滤等具体参数。
- **围绕上下文缺口设计代理协作。** 在 Diego 报销例子里，个人助理代理掌握日历、邮件、Slack、收据；费用系统代理掌握交易、政策、总账账户和历史编码。好的代理交互不要求用户或个人代理选择 150 个 GL code，而是询问“这是客户餐、团队餐还是个人旅行”，再由费用系统应用内部规则完成分类。

## 值得质疑
- 文章对“80/20 已翻转”的判断更像方向性判断，不是严格数据结论；Ramp 的 10 倍增长和 Salesforce 案例能说明早期斜率，但不能证明大多数软件的主要使用已经迁移到代理。
- “两个 LLM 协作”会放大责任边界问题：当用户代理、软件代理、底层系统共同完成任务，错误归因、审计、权限、可解释性会比传统 API 更复杂。文章主要讨论产品设计收益，对安全和治理成本着墨较少。
- 代理反馈更稳定、更具体这一点成立于结构化工具环境；在开放场景里，代理可能把错误假设包装成高置信反馈，产品团队仍需要区分真实需求、模型习惯和提示词副作用。

## 最后一层判断
MCP 不是“给产品加一个接口”的功能清单，而是一种新型产品表面：你以前打磨按钮、空状态和错误提示，现在要打磨工具描述、上下文交换、调用理由、反馈入口和代理之间的分工边界。谁把代理当成一等用户设计，谁就更可能成为未来人类用户背后的默认基础设施。
