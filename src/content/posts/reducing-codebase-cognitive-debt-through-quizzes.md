让 coding agent 围绕代码库向开发者出题，可以有效减少代码演进速度超过个人理解速度所积累的认知债务。Martin Alderson 遇到的困扰是：代码没有出故障，开发仍在推进，自己却逐渐无法确信是否掌握了项目的实际状况。这种理解脱节会悄然累积，形成代码库正在越跑越远的失控感。

他的做法是直接要求 agent 使用 askuserquestiontool，针对当前代码库提出五道难度递增的问题，答完后再解释哪些理解有误。最有价值的环节是围绕错题继续讨论：agent 同时掌握开发者以为代码如何运行，以及代码实际如何运行，因此能够针对两者之间的具体差距作出解释。单纯让 agent 描述某部分代码，缺少对开发者既有理解的检验，也就难以同样精准地纠正误解。

这种检验也适合放在复杂工作开始之前。Alderson 在面对涉及困难方案的复杂重构时，会先让 agent 针对计划或相关项目模块出题；按他的经验，这比阅读大段带有典型 AI 表达习惯的方案说明更容易帮助自己发现问题。同样的方法也能用于复杂电子表格或文档集，甚至可以进一步成为工作流约束：开发者通过针对某项 PR 的测验后，才允许 agent 创建它。

测验还帮助 Alderson 校准了自己的焦虑：他通常发现，感受到的认知债务大于实际存在的理解缺口。通过回答具体问题，哪些部分已经掌握、哪些部分需要补课便有了可核对的依据。让 agent 检验人的理解，既能定位真实盲点，也能减少对项目失去掌控的笼统担忧。
