## TL;DR
真正的 HTML 链接不是"可以点击的东西"，而是浏览器实现的一套完整原生 UI 契约；开发者用 JS 按钮或弹窗替代链接时，剥夺的不只是 UI 功能，而是用户对网页最基本的控制权。

## 核心主张拆解
一个真正的 =<a href>= 链接提供的不是"跳转"，而是浏览器内置的完整交互体系：Ctrl 新标签、Shift 新窗口、Alt 保存文件、右键复制 URL、Tab 键盘导航、搜索引擎与屏幕阅读器可见、悬停预览目标地址。用 JS 按钮模拟链接，以上全部失效。

即使 =<a>= 是真实链接，只要 =onclick= 劫持事件开弹窗，用户同样失去：加载进度显示、取消能力、描述性错误页面、多标签并开、在加载期间阅读原始页面、书签及 URL 分享。慢速网络下弹窗遮盖原页面且无进度提示，是作者认为最高频的体验崩溃场景。

作者并列了其他同性质反模式：无限滚动破坏 Ctrl-F、书签、Home/End 键及返回键；用 5MB JS 框架来传输 100k 文本；重实现原生 =<details>=（破坏搜索工具与屏幕阅读器）；自定义日期选择器（原生 =<input type="date">= 一行即可、自动适配用户格式偏好、自带深色模式）。

## 反驳或薄弱处
文章论点高度依赖"普通用户会主动使用 Ctrl/Shift/Alt+点击"的前提，但大多数用户从不使用这些快捷键；对这类用户而言，JS 按钮与真实链接的体验差异极小，文章对此完全略过，使部分论据在主流场景下说服力有限。技术建议中关于 TCP slow start 与单连接优化的内容过于笼统，缺乏具体数据，与链接主题的关联也偏松散。

## 收束
所有这些反模式共享同一个根因：开发者相信自己能比浏览器做得更好，结果是用更多代码实现了更差的体验。浏览器数十年积累的链接与加载机制本身就是完整的 UI 解决方案，与其对抗不如顺势而为。
