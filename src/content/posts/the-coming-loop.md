## Loop 的到来不可避免，问题只剩如何在 Loop 主导的未来里保住工程判断力

作者 Armin Ronacher（Flask/Jinja2 创作者，现任职 Pi 编码 Agent 平台）区分了两种 loop：Agent 内部 loop（模型调工具、读文件、跑测试）和 harness 层 loop（外部判断"任务是否真的结束"的那个）。他的核心焦虑围绕后者。

### Loop 放大了模型最坏的编码习惯

Karpathy 已指出 LLM 对异常"极度恐惧"。正确做法是让 bad state 无法被写出；LLM 的实际做法是每次遇到局部失败就加一层防御。单次人工引导尚可纠偏；放入 harness loop 后，每轮迭代累积一层防御，系统表面上越来越"健壮"，内部越来越不可理解。作者明说：Claude Code 配合 Fable（全自动、30 分钟不间断）生成的代码比去年秋天有人参与时更差——不是模型更弱，而是 human-in-loop 减少的直接后果。

### Loop 真正有效的两类场景

一是机械转换（Bun 从 Zig 移植到 Rust、MiniJinja 移植到 Go）：可用二进制测试或 LLM 做裁判，结果可核验；二是短生命周期实验（性能 benchmark、安全扫描、研究探索）：代码不需要长期维护。共同特征：产出物是已有代码的变换，或故意无需持久存活。原创、需要长期维护的生产代码目前不在有效范围内。

### 你无法彻底退出

curl 案例：AI 几乎不参与 curl 核心开发，但维护者已被 AI 生成的漏洞报告淹没。防御方迟早也要上 loop 才能跟上报告速度。竞争维度同理：五个人做五十人的活的团队已经存在，甚至有人让机器对着你的产品循环跑"把它变成另一个"。

### 最深的风险：认知依赖

作者区分了两种依赖：钱包依赖（成本上涨就痛苦）和认知依赖（团队失去不借助 clanker 就理解代码的能力）。如果代码库假设机器参与是维护模型的一部分，那么当模型访问被贸易限制切断、成本不可承受、或能力回退时，整个系统就失去了人类可维护性。这已在发生：越来越多人合并自己无法完整解释的代码，越来越多人通过 LLM 的间接层与同事沟通。

### 软件从机器变成有机体

我们过去相信软件是可分层理解的确定性机器；现在正在接受"诊断但不理解"的模式——像医生观察症状、假设病因、做测试、用药、再观察。与医学不同的是，软件的"有机体化"是工程选择造成的，而不是固有复杂性的结果。

### 结论：问题不是"是否 Loop"，而是"如何在 Loop 里保留判断力"

作者没有给答案，但提出了正确的问题：harness loop 主导的未来里，如何不让人类角色退化为"消息传递者"，如何在架构层面保住可监督性，如何重新定义负责任的工程实践。
