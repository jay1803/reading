## TL;DR
形式化验证在这次案例里并没有失效，它恰恰证明了自己有效: 1.058 亿次模糊测试几乎没能在已验证的 Lean 应用代码里打出经典内存漏洞，真正暴露出来的风险集中在证明边界之外, 一个是根本没被证明的 ZIP 解析器，一个是所有证明都默认可信的 Lean 运行时。

## 核心主张拆解
作者把 lean-zip 当成一次很罕见的压力测试对象: 这是一个由 10 个 agent 构建并在 Lean 中端到端证明过正确性的 zlib 实现，核心定理保证压缩再解压会返回原始数据。为了避免让 Claude 因为“这段代码被证明过”而先入为主，作者故意删掉定理、规格和文档，只保留经证明的 Lean 实现，然后让 Claude 配合 AFL++、ASan、UBSan、Valgrind、静态分析和手写 exploit 样本连续轰炸。

结果很硬: 16 个并行 fuzzer 跑了约 19 小时，覆盖 6 个攻击面，完成 105,823,818 次执行、359 个 seed，打出 4 个 crash。结论分成两层。第一层是最亮眼的正面结果: 已验证应用代码里没有堆溢出、没有 use-after-free、没有栈溢出、没有越界读、没有 UBSan 报错。作者认为，这说明 Lean 的类型系统、依赖类型和递归约束，确实把传统 C/C++ 压缩库里一整类 CVE 结构性地消掉了。

第二层是两个真实漏洞都落在“没被证明”的地方。其一是 lean-zip 的 Archive.lean 从 ZIP 头里直接拿 compressedSize 去申请内存，没有先和真实文件大小做一致性校验，于是一个 156 字节的伪造 ZIP 就能把程序打到 OOM panic。这不是验证失败，而是验证根本没覆盖到 archive parser。其二更关键: Lean 4 运行时的 lean_alloc_sarray 在计算分配大小时会发生整数回绕，导致接近 SIZE_MAX 的 ByteArray 容量最终只分到一个极小缓冲区，随后 fread 还会按超大长度写入，形成 heap buffer overflow。这个 bug 影响的是 Lean 4 的信任根，不是某个应用局部模块。

作者借此把结论收得很准: 形式化验证能显著压缩 bug 面积，但它不能自动扩展到你没写规格的模块，也不能替你证明底层运行时、编译器和其他 trusted computing base 组件正确。证明的强度，取决于你证明了什么，以及你选择相信什么。

## 反驳或薄弱处
- 这是一次高强度个案，不是大样本比较实验。它足以说明“验证覆盖范围很重要”，但还不足以量化验证相对普通工程流程到底提升了多少安全边际。
- 作者把定理和文档删掉后再交给 Claude 盲测，这有助于减少模型偏置，但也改变了真实代码库形态，因此结果更像一次安全压力测试，不是对原仓库开发流程的完整复盘。
- 文章把“AI 降低找洞成本, 软件危机将至”作为开场大前提，但正文真正给出的强证据仍然集中在 lean-zip 这一例上，宏观外推主要靠趋势判断。

## 谁来验证验证器
这篇文章最值钱的地方，不是“我在被证明正确的程序里找到了 bug”，而是它把验证的收益边界画清楚了: 证明不是魔法护盾，它更像一道高压围栏。围栏里面的代码变得异常难打，攻击者于是转去撬围栏外的解析层、运行时和信任根。验证没有终结安全工作，它只是第一次让你真正知道下一层该怀疑谁。
