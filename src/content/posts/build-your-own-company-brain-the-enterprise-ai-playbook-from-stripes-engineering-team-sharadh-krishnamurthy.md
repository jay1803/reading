## 嘉宾背景

Sharadh Krishnamurthy 是 Stripe 的工程经理，参与开发内部 AI 助手 Kai。他此前一直从事工程工作，也做过 Stripe 的开发平台和数据平台相关工作；开发 Kai 初期，他曾暂时以个人贡献者身份参与实现。

## TL;DR

Kai 的演示从一张数据看板开始，但访谈反复回到看板背后的条件：员工不必自己选择模型、寻找可信数据或为每个工具重新判断权限，因为这些决定可以由熟悉业务的人按项目和工作流预先配置。Sharadh 同时强调，这种便利依赖能承受 agent 行为的基础设施；系统已经遇到过险些影响核心服务的问题，也远未定型。

### 1. 企业 AI 要把公司特定的上下文与使用边界放在一起

Sharadh 说，2026 年初已经有大量强大的 AI 工具，他和同事 Anoop 面临的问题却是如何让 Stripe 各类员工都能使用 AI。Stripe 的产品、地区和流程繁多，仅仅提供一个模型，不能保证它理解员工正在做什么，或按公司的方式办事。因此他们把上下文和治理一起纳入 Kai。

Kai 默认知道使用者是谁、在组织架构中的位置；连接的内部工具还能提供 OKR、项目和近期团队信息。对于 Google Drive、Slack 及私人消息等更敏感的内容，员工可以选择开放多少访问权限。Sharadh 自己会按会话或按天开关访问，而另一些员工愿意让 AI 使用更多上下文。Kai 运行在云端，置于 Stripe 的标准安全边界之内，但他并没有把"知道得越多"当成适用于所有人的默认答案。

### 2. Projects 让任务目的成为 AI 配置和治理的单位

在 Sharadh 看来，进入一个 project 等于向 Kai 表明自己要完成什么工作，而不只是把聊天归档。一个 project 可以服务五人或数百人；熟悉该领域的负责人可以为成员选定相关 skills、适合任务的默认模型，以及成本、性能、延迟之间的取舍。它还可以针对团队或短期任务设置不同边界，甚至以另一套 agent 和后端运行，而不是一律使用通用配置。

工具权限也按工作目的设置。Sharadh 举例说，处理敏感资料的 HR 员工既不能让 agent 随意把资料写进全公司可见的 Google 文档，也不应因此被禁止使用所有工具。project 的 tool policy 可以要求某些动作先由人确认；他用创建日历邀请演示了这种流程。Claire 指出，相比每人每次自行开关连接器，团队共享的权限配置能减少日常判断。Sharadh 补充说，如果每次工具调用都弹出确认，员工终究可能误按，过多摩擦本身也会带来风险。

### 3. Agents 会放大基础设施故障，因此韧性必须考虑其行为方式

Claire 注意到，agent 在不确定时可能以大量查询反复尝试。Sharadh 认同：agent 会以出乎预料的方式使用系统，把原有故障模式放大。Stripe 早先为数据查询层做的韧性建设，让它能够承受 agent 的高频使用；但上线初期仍出现过 agent 失控的情况，有些据他所说可能险些影响核心系统。团队及时发现问题，随后加固了相关系统。

他还提出要识别"这是一个 agent，以及它正为哪种用途工作"，以便决定请求优先级和何时削减负载。不过他明确说，agent 身份识别这个问题尚未解决。

### 4. 可靠的数据 agent 应先沿用可信的分析路径，再编写新查询

演示中，Sharadh 请 Kai 找到他平常用来追踪 Kai 使用情况的 Hubble 查询，并据此生成看板。他指出，agent 即使答出了问题，也未必知道自己选的是不是正确的表和指标。Stripe 原先为人建立的数据目录、schema 信息、分层数据集、关键指标所在的分析层，以及既有报表和查询，因而也成为 agent 判断数据来源的依托。

数据科学家把优先使用可信来源的做法写进 data skill：先找能直接回答问题的现成产物或分析来源，再沿既有查询和数据层逐级回退，必要时才到目录中寻找合适的数据集并构造新查询。Sharadh 在不同段落中描述中间层的次序略有差异，但一致强调不要一开始就让 agent 随意查询底层数据。Claire 认为，这些原本让人更有效率的平台投入，也让 agent 有了可遵循的路径。

### 5. 可迭代的产物让非工程师完成自己工作流的"最后一公里"

Kai 用找到的数据生成了一张带链接的交互式看板。Sharadh 随后要求它加入新的细分数据并进行汇总变换；更新结果出现在同一张看板里，而不是重新制作一份。他说，保留产物既避免每轮都丢弃 HTML、重新消耗 token，也让人与 agent 能在多轮对话中持续修改同一项工作。

他之所以重视这一点，是因为各团队需要的数据处理方式差别很大：集中制作足以覆盖所有岗位的看板，会产生大量难以维护的版本。有了隔离的云端 sandbox，非工程师也能让 agent 代写代码，把数据做成贴合某次会议或某项工作的轻量应用，而不必先学会实现它。

### 6. 共享 skills 能把个人成果变成工作流，但效果取决于检索与维护

Sharadh 希望把一次成功的看板制作过程打包为可重复使用的 skill，供自己或团队调用。Kai 可以根据会话生成草稿，填写描述和适用时机；用户再编辑、测试，并决定保留为私人 skill 还是分享出去。演示时他发现草稿此前已经建过，因此这段展示并非一次从零完成的新建流程。

创建之后，还必须找得到。Sharadh 用一句简短的看板请求演示 Kai 识别相关 skill；与处在文件夹和仓库层级中的 coding agent 不同，企业员工的任务可能横跨多个系统，没有天然的目录层级可供检索。他说 Stripe 约有两千个 skills，平台会关注哪些被正确调用，并给作者改进建议。使用数据也帮助维护者判断哪些值得纳入通用工作流，哪些应留给特定团队：高频使用的有数十个，另有服务小团队的长尾 skills。对他而言，无关 skill 占用的上下文本身就可能降低结果质量，但使用人数少并不意味着一个专业团队的 skill 没有价值。Claire 提到的定期归档、删除机制是她见过的其他做法，Sharadh 没有说 Kai 已实施同样的规则。

### 7. 小型原型让抽象的企业需求变得可见，从而推动采用

Sharadh 说，在强大的 coding agents 已经存在时，很难只靠解释说清为什么还需要内部 agent。他和同事用约一名半工程师、两周时间做出初版；有了可展示的产品，许多问题才容易讨论。随后，GTM 团队的合作者及其他试用者带来了早期需求。试点阶段约有两三百名用户、两三人参与开发；一次全公司演示后，使用量明显上升。

据 Sharadh 当时的说法，Kai 每周有超过一万名使用者，管理核心体验的团队不到十人。他将这归功于 coding agents 带来的生产力，也明确归功于开发平台团队、既有工具和此前积累的基础设施，而不把成果全算在小团队身上。访谈末尾他强调，他们并未认为设计已经完成，随着技术变化，Kai 还会继续调整。

## 提到但未深入展开的话题

Sharadh 用手机上的 Gemini 回答六岁孩子关于系外行星和星系的问题，也用 Kai 的 schedules 提醒自己未完成的工作。他谈到 AI 出错时通常会礼貌地重新提出要求；节目末尾还提及招聘、联系渠道、赞助内容和收听方式。
