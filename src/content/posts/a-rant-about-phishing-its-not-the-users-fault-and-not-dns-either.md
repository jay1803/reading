网络钓鱼之所以屡屡得手，核心责任不在缺乏警惕的用户或 DNS 的设计，而在于组织主动破坏了域名作为身份标识的可信度，把正常登录流程做得与骗局几乎无法区分。现实中的企业认证可能连续跳转于公司官网、登录子域名、第三方供应商域名、带 UUID 的路径、云服务域名和 API 地址之间，用户名、密码与 2FA 输入框甚至全部托管在公司主域名之外；再加上 token 过期后随机弹出的认证窗口，用户逐渐习惯在任何陌生页面看到公司 Logo 就输入凭证。攻击者于是只需仿制一个带密码框和企业标识的网站，无须设计特别可信的 URL，因为合法服务早已训练用户忽略地址栏。

URL 本身确实不够直观：协议和 hostname 从左向右由具体变得一般，路径却从左向右由一般变得具体，而最能说明网站归属的二级域名又位于整条地址中间。例如 `https://funnies.maurycyz.com/memes/crow_hobbies.jpg` 表示访问由 `maurycyz.com` 运营的 `funnies` 服务器上、`memes` 目录中的 `crow_hobbies.jpg` 文件，其中真正需要识别的是 `maurycyz.com`。非技术用户应当学会查看这一部分，仅仅被告知"不要点击可疑链接"并不能形成可执行的判断标准；但如果正规机构自身频繁使用第三方域名和形似钓鱼的地址，即使用户掌握了 hostname 的结构，也无从据此判断真伪。

要让用户有机会识别骗局，组织必须长期使用一个单一、知名且稳定的根域名，并把内部服务放在它的子域名下。**company-auth.com**、**company.someone-else.com**、**someone-else.com/company** 或 **auth.someone-else.com/[UUID]** 这类地址都应被禁止，因为它们在归属关系上与诈骗网站没有可辨识的差别。该要求对登录页尤其关键，因为仿冒登录页可以直接窃取密码和 2FA 凭证；它也应覆盖调查问卷、客户服务及其他日常页面，让用户形成"该组织的链接始终属于同一根域名"的稳定习惯，从而降低社会工程攻击的成功率。

邮件和短信里的链接同样必须位于组织可识别的域名下。确实需要导向外部供应商时，可以先提供诸如 **company.com/survey** 的本地域名入口，再由它重定向到第三方调查平台。这样做并不要求组织亲自托管所有系统，因为许多 SaaS 服务支持自定义域名，而创建短链接或重定向几乎没有成本。相同原则也适用于电话号码：消息中直接要求用户拨打一个陌生号码，会让收件人无法验证其真实性；可靠做法是把联系方式发布在组织官网的页面上，再从消息中链接到该页面。

有人因钓鱼泛滥而指责子域名机制本身，甚至认为它让犯罪者可以随意冒充任何机构，但 DNS 的层级结构四十多年来基本没有改变，理论上足以清楚表达每个网站由谁运营。真正的问题是企业、服务商乃至政府没有一致使用自己的根域名，反而投入大量精力建立跨越多个陌生域名的合法流程，系统性地抹除了正规网站与骗局之间原本可供辨认的边界。**安全教育只有在组织先提供稳定、可验证的身份信号时才有意义；当正规服务主动把可疑外观常态化，要求用户独自识破钓鱼就是把制度设计的失败推给受害者。**
