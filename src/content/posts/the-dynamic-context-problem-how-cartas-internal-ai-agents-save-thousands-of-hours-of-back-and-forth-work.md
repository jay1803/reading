## TL;DR

Carta 的 AI agent 并没有靠自动化"消灭"重复劳动来节省成本——而是靠动态组装上下文来"放大判断力"：每月 2 万到 2.5 万次现金对账任务，每次从 11 分钟压缩到秒级，省下 3500 小时/月，但更大的价值是让原本孤立在各团队的知识开始在组织内流动。

## 核心洞见：为什么"上下文"才是瓶颈

Carta 的基金管理业务有 600 名员工服务 2500 家客户，核心难点不是技能不足，而是**上下文获取的工业工程问题**：每一次问题处理都要跨系统、跨团队拼齐信息碎片，才能做出判断。Tikmani（ML 总监）的选题原则是：找那些"判断力本身不可省略，但获取判断所需上下文的过程可以自动化"的工作流——而非把 AI 当降本工具。

第一个落地场景是脉冲检查 agent（balance sheet/income statement 差异诊断），验证可行后才扩展到现金对账。

## 具体机制：上下文如何被工程化

- **Lucidchart 作为 agent 的"源代码"**：领域专家在 Lucidchart 中画完整决策树，内部工具将其转为 JSON 注入 agent 系统 prompt。agent 每次运行拉取最新版决策树，业务团队可自行维护逻辑、无需工程师介入。
- **不微调，靠 in-context learning**：用基础模型 + 丰富上下文，绕过了定制模型的高投入。pgvector 做语义搜索，辅助检索相关历史交易和客户备注。
- **构建信任的 UX 设计**：暴露工具调用和中间结果，让用户能区分"模型推理出错"和"输入上下文有误"；允许用户从出错的那一步重跑，而非重头开始。
- **原型阶段故意延迟 UI**：把智能层（prompt、上下文）与产品层解耦，让两者独立迭代——这是让"快"真正可能的架构决策。

## 隐藏限制

评估体系目前主要靠内部用户直接反馈，缺乏结构化 eval 框架（Tikmani 承认这是早期产品的现实）。系统提示词和上下文的小变化可能导致输出漂移，但团队尚未建立 baseline test suite 来保障模型/prompt 替换时的稳定性。

## 留下来的那个想法

Lucidchart 变成 agent 的"源代码"这件事，本质上是把**提示工程的权限还给了最理解业务的人**——不是因为工程师偷懒，而是因为这才是正确的权责归属。这个模式一旦成立，ML 团队的角色就从"写 prompt"变成了"维护让业务团队能安全写 prompt 的基础设施"。
