Staff Engineer 找到高价值问题的关键，在于长期浸泡于组织的日常工作，持续吸收各团队遇到的阻力，让零散问题积累、相互印证并显露共同结构，而非专门腾出时间凭空"思考战略"。只等待经理或负责人分配任务、再解决其中最难的部分，同样可能带来晋升，但作者职业生涯中影响最大的项目，往往源于发现并解决领导尚未意识到的问题。这种工作方式尤其适合大型公司的基础设施和开发者工具团队，因为工程师拥有自下而上的路线图影响力；在高度自上而下的组织里，相应空间会更小。

发现问题首先要吸收用户的处境，而不是照单全收他们提出的功能请求。会议、聊天、演示和邮件里每天都有人描述工作为何困难、哪些环节拖慢了进度，以及他们希望获得什么能力；当这些内容与自己的职责范围重叠时，作者会继续追问目标、现有产品为何失效，并用"如果 X 存在，是否能解决问题"或"已有功能覆盖了多少场景"来检验理解。因为用户常把自己设想的方案包装成需求，只有深入观察其工作流程、陪他们排查 bug，甚至亲手重现问题，才能辨别真实需要与表面请求。作者还会主动联系负责关键系统、横跨多个团队或熟悉下游工作的同事，通过 1:1 或 coffee chat 借用他们更广阔的组织视野；这些人可能已在多处见过同类现象，能显著缩短识别模式的时间。

问题被发现后不应立即变成项目。作者曾因某个声音很大的团队热切要求一项功能而迅速实现它，结果对方几乎没有使用：团队优先级已经改变，或者请求只服务于一次不再重要的调查。某一时刻的迫切程度无法代表该功能相对于产品全部责任的真实重要性，过度聚焦单一请求还会遮蔽整体图景。因此，等待本身是一种筛选能力：同一问题若在不同团队独立出现，优先级就会提高；表面不同的问题可能逐渐显露相同结构，从而由一个方案覆盖多个场景；有些请求则会随着时间自然消失，证明提出者原本就没有那么在意。

保留这些尚未解决的问题，需要让证据有机会继续累积。作者通常先在脑中记下，等问题再次出现时重新审视，也有工程师使用更系统的记录方式；具体机制取决于个人习惯，核心是不要让第一次听到的诉求立刻主导路线图。持续吸收会产生远多于个人或团队处理能力的问题池，而重复出现的频率、涉及团队的范围、阻塞程度以及彼此之间的关联，才逐步构成是否值得投入的依据。

Perfetto 的演进展示了如何从大量具体请求中识别共同结构。Perfetto 是一款性能调试工具，用由多行 **tracks** 组成的时间线展示系统活动。数年间，有团队要求把自己偏好的 tracks 固定在屏幕顶部，另一些团队也要求固定完全不同的 tracks；还有人希望打开记录时自动缩放到特定区域，或显示针对自身需求设计的聚合视图，甚至有人用 bookmarklets 搭建了复杂变通方案。作者没有逐项实现，而是在长期积累后意识到，这些团队都希望按照自己的工作流定制 Perfetto，同时不把个人选择强加给所有用户。真正的共同需求是扩展 UI 的能力，多个别扭的功能请求因此收敛成一个更有杠杆率的平台问题。

这种收敛带来的优雅感仍然只是假设，不能替代验证。作者曾认为，为 Perfetto trace 查询建立透明缓存，可以同时解决大型 trace 的共享问题和重复查询问题；直到撰写 RFC 并制作原型时，他才发现二者需要不同方案，于是拆成两个设计，之后两部分都成功发布。这个案例说明，所谓"共同形状"可能只是设计者对统一方案的偏爱，必须通过写作、原型和实际约束暴露其中错误。

投入强度应随价值、风险和确定性调整。低风险且明显有用的改动可以直接提交并告知经理；技术可行性或成本不确定时，应先制作一次性原型，让失败点暴露出来，也让其他人能针对具体事物反馈；规模很大但判断已较充分的想法，则可能需要数周或数月实施，并争取多个工程师和团队的支持。整个过程中，作者也在说服自己：如果用户看不到价值，或出现重大技术障碍，及时停止胜过交付无人使用的功能或制造长期维护负担；若方案成立但组织时机未到，则先搁置，等它成为优先事项时再启动。问题发现与塑形本身已经能够改变组织方向，提出者无需亲自承担全部实现。

Perfetto 的扩展能力最终值得完整投入。当时团队已经用 plugins 模块化 UI，但所有 plugin 代码都必须开源，许多 Google 内部场景无法接受这一条件。作者先向经理、队友和客户团队说明问题与提案，随后撰写两份 RFC，进行多次 1:1 和几场演讲，并根据反馈持续修正设计。最终交付的 **macros** 成为"轻量级扩展"，允许用户无需编写 plugin 就能自动执行 UI 操作；**extension servers** 又让团队可以共享 macros。Perfetto 团队因而无需逐个实现所有定制请求，而是赋予用户自行适配工具的能力。如今 Google 内部已有数十个团队使用 macros 和 extension servers，其他一些公司也在内部部署 extension servers。

解决高价值问题还会形成自我强化的循环。持续认真倾听、提出有用问题并真正帮助他人后，人们会更早带着问题来找作者，也会把他引入其他存在相关困难的讨论；更广阔的信息流又提高了发现跨团队模式和真实需求的概率。早期，作者必须亲手把许多想法做成成果，以证明自己的判断可靠；随着长期 stewardship 建立信任，经理和组织开始赋予其判断更高权重，他便能在不拥有每个项目的情况下影响路线图。对他而言，谈话是技术产出的输入，工程实现依然是重要结果。Staff Engineer 的战略判断由此成为日常技术工作的延伸：在足够长的时间里贴近他人的真实工作，才能看到任何单一请求都无法呈现的组织级问题。
