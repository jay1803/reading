## TL;DR
AI 编程真正带来的风险不是“代码写得太快”，而是把产品发现重新拉回 2001 年 Agile 的代码优先路径：团队因为一天就能做出漂亮原型，反而更容易跳过低成本验证、问题澄清和证据积累，最终用更快的速度制造更昂贵的认知偏差。

## 核心主张拆解
作者反驳 Henrik Kniberg 著名的“滑板到汽车”MVP 图，并不是否定迭代、用户反馈或用代码测试，而是认为这套解释把 discovery 过度绑定到 working code / release。Kniberg 的版本强调先交付能解决“从 A 到 B”的最小可用方案，再逐步迭代到汽车；它在 Agile 语境里合理，因为当时用户研究、行为数据、Lean Startup、增长实验等工具还不成熟。

今天的产品发现工具箱已经更宽：商业建模、数据分析、用户访谈、问卷、fake door、concierge、wizard-of-Oz、可用性测试等，都可以在写代码前验证关键假设。作者的 AFTER 模型把 28 种验证方法铺成一条从低成本到高成本的路径，最佳实践是先用便宜的 no-code 技术筛掉或调整弱想法，再把开发资源投入已有支持证据的方向。

AI coding 让“先写代码”重新变得诱人。Claude Code、Figma Make、AI 使用指标、token leaderboard、PM 必须写代码等现象，会把组织注意力从学习速度转向产出速度。一旦管理层重新相信 working code 才是进展，就会出现两种退化：第一，直接跳到用户测试代码，忽视数据、调研和假设拆解；第二，认为 discovery 已经过时，既然代码便宜，就 launch-and-iterate。

## 具体机制
用户测试的瓶颈通常不在写代码，而在确定目标用户、招募样本、设计沟通协议、埋点或测试脚本、让用户真正参与、等待实验运行、收集和分析数据。AI 可以加速其中一部分准备工作，但不能把真实用户行为的时间压缩到零；在 B2B 或大规模实验里，测试周期仍可能以天、周甚至月计。

漂亮原型还会放大承诺升级偏差。团队、经理和利益相关方一旦看到可运行的软件，就更容易把它当成准产品，而不是一次性验证工具；即便测试结果很差，也更难果断停止。这使 AI 原型从“学习工具”滑向“沉没成本生成器”。

作者也把自己的 meme 当成反例：他本可以先 Google Kniberg 的原文，理解对方语境后再表达观点；但 AI 让生成精美图示太容易，他直接行动并发布，跳过了最基本的思考验证。这个例子强化了文章的核心警告：AI 降低执行摩擦，也会降低人们做前置判断的耐心。

## 反驳或薄弱处
文章把“代码优先 discovery”与“AI coding 热潮”连接得很有现实感，但主要证据是行业观察和若干现象信号，没有提供系统数据证明组织已经大规模回退到 Agile 式 release-first。它更像一篇及时的产品判断，而不是实证研究。

作者对 no-code 验证的推崇成立，但不同产品类型的边界没有展开。某些 devtool、AI workflow、底层交互或性能敏感产品，价值确实可能只有在真实软件中才显现；这类场景下，“先代码测试”未必是懒惰，也可能是最短证据路径。

## 最后一层
AI 编程应该被放进 discovery 工具箱，而不是替代 discovery 本身；真正稀缺的不是代码产能，而是组织在行动变容易之后，仍愿意慢下来判断什么值得行动。
