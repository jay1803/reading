## TL;DR
好的系统设计看起来"毫无亮点"——没出什么事、比预期容易，这才是成功。复杂系统往往是糟糕决策的补偿产物，而非能力的体现。

## 核心原则拆解

**最小化有状态组件。** 无状态服务出问题可以直接重启恢复；有状态服务一旦写入了坏数据，必须人工介入。原则是：让一个服务"拥有"某张表的写权限，其他服务通过 API 或事件请求它，而不是五个服务各自乱写同一张表。

**数据库是瓶颈核心，索引优于缓存。** 高流量应用的瓶颈几乎总在数据库。先把查询交给数据库做（JOIN 而非内存拼接），先加索引，再考虑缓存——用缓存掩盖一个没加索引的慢查询是反智的。索引字段顺序遵循高基数优先。

**慢操作必须分离到后台任务。** 对用户的最小必要工作同步完成，其余进入队列异步处理。后台 job 系统（队列 + 执行器）是比自研任何方案都更成熟的路径。远期定时任务用数据库表 + `scheduled_at` 列而非 Redis 队列。

**缓存是状态，警惕其成为 bug 来源。** 资深工程师想缓存的东西比初级工程师少，因为缓存本身是状态，可以持有脏数据、产生难以追踪的 bug。能用索引解决的，不要用缓存解决。

**热路径决定架构空间。** 系统中"触发频率最高"和"最不能出错"的路径设计选项最少、出错代价最大，应优先设计。一个 billing settings 页面有一千种写法，但消费所有用户行为的数据流可能只有少数几种合理选择。

**失效策略必须显式设计。** 限流检查的 Redis 挂了，是放行还是拦截？每个依赖组件都需要明确的 fail-open 或 fail-closed 策略。熔断器防止级联超载，幂等键防止重试引发的重复写入——两者都不是"可选优化"，而是基础能力。

## 值得质疑处
文章对 push vs pull 的讨论在大规模场景下点到即止，并未给出明确的选择依据（作者自己也说"我觉得两种都差不多"）。这对于需要在百万客户端规模下做架构决策的读者来说帮助有限。

## 留下的那个想法
"好设计是自我消除的"——最好的系统决策会让自己隐形，让人以为"这块没什么设计"。而工程师的本能是被复杂度吸引、把复杂当能力，这个认知偏差本身才是系统烂掉的根源。
