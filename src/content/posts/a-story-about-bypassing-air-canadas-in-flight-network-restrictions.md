## TL;DR
作者把一次 12 小时航班上的“免费文字消息”网络，当成了一个现实版网络攻防题来拆：机上网络并非彻底断外网，而是通过白名单和端口策略把大多数流量卡死。真正的突破点不在伪装域名，而在发现任意 DNS 服务器的 53 端口 TCP/UDP 流量都能出去，于是他们把代理服务伪装成跑在 53 端口上的“DNS”，成功把 GitHub 之类原本被禁的网站打通。

## 关键洞察
故事的起点很简单：加拿大航空的机上 Wi-Fi 对未付费用户只开放 WhatsApp、WeChat 这类“免费文字消息”，正常网页访问要额外付费。作者想验证的核心问题是，这种限制到底是按应用、按域名、按 IP，还是按更底层的网络出口规则来做的；只要判断清楚限制层级，就有可能找到绕过办法。

他先测试了最直观的一条路：既然 acwifi.com 登录页能打开，而 github.com 不行，那限制会不会只发生在 DNS 解析层？如果只是 DNS 白名单，那么把自己的代理服务器 IP 写进 /etc/hosts，伪装成 acwifi.com，再配合自签证书做中转，理论上就可能把请求偷偷转出去。这个思路的关键假设，是网络允许你连任意外部 IP，只是不给你解析非白名单域名。实际测试很快把这个假设打掉了：无论是自己的服务器 IP，还是 Cloudflare 的 IP，ping 都不通；进一步用 curl 直连 443 端口，也在 TLS 握手阶段失败。作者后来看了 Hacker News 评论，也补充说明了“ping 不通不等于 IP 一定被封”，但他已经验证过，问题不只是 ICMP，被拦的是更广义的外连能力。这说明机上网络大概率不只是做 DNS 过滤，而是配了更严格的出口白名单。

第一条路走不通后，他们换了一个问法：有没有哪种外连流量是系统必须放行的？答案是 DNS。作者用 dig 查询域名，发现正常 DNS 请求可以出去；更关键的是，换一台任意指定的外部 DNS 服务器继续查，也能返回结果。这一步把结论推进了一大截：机上网络并不是只允许访问自家 DNS，而是对外部 53 端口相当宽松。

接着他们又验证了一个决定成败的细节：53 端口上的 TCP 流量是否也能通。因为如果只放 UDP，就更像“只让你做标准 DNS 查询”；如果 TCP 53 也能通，就意味着策略可能只是粗糙地按端口放行。实验结果是 TCP DNS 也成功了，于是他们意识到，网关很可能根本不检查 53 端口上跑的是不是真 DNS，只是把“去 53 端口的流量”统统当作 DNS 放过去。

这时真正可利用的漏洞形状就出来了：既然系统信任 53 端口，那就把代理服务器直接部署在 53 端口上。作者的室友用 xray 搭了一个跑在 53 端口上的代理，作者本地再把流量转进这个 SOCKS 代理，结果 curl 通过本地代理访问 GitHub 时成功拿到了响应。突破点因此非常明确：他们并没有伪造 DNS 报文，只是把“非 DNS 的代理流量”塞进了一个会被系统误判为 DNS 的端口里，利用的是网关基于端口号的粗粒度放行规则。

文章没有停在“已经成功”这里，还继续往前推了一层：如果航空公司的网关更严格，会去检查 53 端口里的内容是不是像真的 DNS 请求，那这一招就会失效。对应的更强方案是 DNS Tunnel，也就是把真实数据封进合法的 DNS 查询里，例如用 TXT 查询承载内容。这样从包内容上看，它仍然像真的 DNS 通信。作者提到 iodine 这类工具能做到这一点，只是他当时机上电脑没装，最终没有实测。

正文结束后还有一个很有意思的 follow-up。有人说即便绕过网站访问限制也没意义，因为免费文字消息的带宽上限才是真正瓶颈。作者的回答是：从系统设计上看，带宽限制未必是跟“你当前跑的协议”绑定，更可能是把已付费设备的 MAC 地址放进高带宽白名单。若真如此，理论上可以通过 ARP spoofing 冒充已付费用户的 MAC 地址来蹭到更高带宽，甚至还能通过遍历局域网内已知 MAC 去撞出付费用户。这一段的价值不在“教人怎么做”，而在于它把整套收费网络的控制面又拆开了一层：访问权限和带宽权限可能是两套不同机制。作者也明确把这一步划为真正越界、带有明显违法风险的做法，只停留在原理讨论，没有实践。

整篇文章最有意思的地方，是它不是在炫一个单点技巧，而是在展示一种很工程化的排障路径：先猜限制可能落在哪一层，再用最便宜的实验逐层排除，最后把系统真正信任的通道找出来。最终他们确实“拿到了外网”，但也发现飞机带宽烂到几乎没法好好上网，技术上赢了，体验上也没变成什么天堂。

## 一句话总结
这篇文章写的其实是一次标准的分层排障：先确认机上网络封的是域名、IP 还是端口，最后抓住“53 端口被粗放信任”这个漏洞，把代理伪装成 DNS 出口，从而绕过了免费短信网络的访问限制。
