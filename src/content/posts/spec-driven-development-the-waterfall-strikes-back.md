## TL;DR
这篇文章在讲：**Spec-Driven Development 把编码代理前面又加回了一层很重的规格流程。** 做法是先生成需求文档、设计文档、任务清单，再让代理按这些文档写代码。问题是，这套流程会制造大量 Markdown、重复审查和额外管理成本，最后并没有真正消除不确定性。文章给出的替代方案是把需求拆小，按 Agile 的思路一轮一轮验证假设，用自然语言直接驱动编码代理迭代实现。

## 关键洞察
文章先解释了 SDD 怎么工作。开发者先给一个初始 prompt 和一些说明，LLM 再生成产品规格、实现计划和任务清单。文档之间是串联关系，前一份文档会生成后一份文档，开发者也可以手动修改这些文档，再交给 Claude Code、Cursor、Copilot 这类编码代理执行。

这套方法的问题，文章拆了几层。

第一层是 **文档体积会迅速膨胀**。哪怕只是一个小功能，也可能生成很多个 Markdown 文件和上千行文字。开发者后面花掉的大量时间，不是在判断产品和代码，而是在读这些文档、找里面的错误和遗漏。

第二层是 **文档并没有真正解决上下文问题**。SDD 里的代理和编码代理一样，还是通过文本搜索和文件导航理解项目。它们依然会漏掉已有代码里需要一起改动的地方，所以功能评审和技术评审还是少不了。

第三层是 **流程过重**。需求、设计、任务三段式流程对大多数功能都太大了。里面会出现很多重复内容、假想边界情况和过度展开的细节。文章还提到，很多工具生成的“用户故事”写法本身就不准确，只是看上去像敏捷术语。

第四层是 **审查成本增加了**。技术规格里已经开始出现代码，所以开发者要先审规格里的代码，再审真正生成出来的代码。最终实现还是会有 bug，这就等于把本来就要做的审查工作又复制了一遍。

第五层是 **规格不能保证代理照做**。文中举的例子里，代理把“验证实现”标成完成，但实际上没有写任何单元测试，只写了手工测试说明。也就是说，规格文档会带来一种可控的感觉，实际执行时依然会偏。

第六层是 **收益会随项目规模下降**。SDD 在从零开始的新项目里还能有一点作用，项目一旦变大、变旧、上下文变复杂，规格更容易偏离实际，维护成本也会越来越高。文章对大型已有代码库的判断很明确：这套方法基本不好用。

文章接着往后推了一步：问题不只在工具还不成熟，也在方向本身。SDD 想解决的问题其实是“怎么把开发者从软件开发里移走”，做法是用更细的前期规划把编码代理圈起来。这个思路很像瀑布式开发和 Big Design Up Front：先堆很多设计，再让后面的人去实现。文章的判断是，软件开发本来就是高不确定性的过程，前面写更多规划，并不会把这种不确定性消掉，只会提前堆出更多假设。

还有一个现实问题是：SDD 并没有真的把开发者拿掉。需求阶段需要能识别业务错误的人，设计阶段需要能识别技术错误的人。所以它要求的其实是同时懂业务分析和工程的人。文章把它和 No Code 工具放在一起看，意思是两者都在承诺“减少开发者”，实际还是要开发者来使用和兜底。

后半部分给出的方向是 **回到 Agile 的适应性**。文章的思路很简单：编码代理面对简单问题时更稳，那就不要把复杂需求翻译成复杂设计文档，而是把复杂需求拆成多个简单问题，逐个实现、逐个修正。

文中给出的循环是：
- 找出当前产品里风险最高的假设；
- 设计一个最简单的实验去验证它；
- 开发这个实验；
- 如果失败，就继续调整；如果成功，就进入下一轮。

文章还给了一个实际例子：作者用 Claude Code 做了一个 3D 雕刻工具，整个过程没有写规格文档，就是一小步一小步加功能，代理理解错了就纠正，自己的想法效果不好也继续改。因为每一轮实现都比较便宜，所以通过连续小步试错，会更快逼近可用的产品。

这篇把这种方式叫做 **Natural Language Development**。核心意思是，直接用自然语言推动产品 backlog 前进，在实现中看结果，在结果里继续修正。文末也补了一点当前限制：编码代理现在主要还是文本交互，如果要更准确地指出界面某一块、布局和视觉细节，现有工具还不够，后面更值得补的是视觉交互能力。

## 对你（行动层面）的启发
这篇最实用的点，是把和编码代理协作的工作方式往前推了一步：
- 先别急着写大规格，先看这个问题能不能拆成更小的单元；
- 优先把当前最不确定、最有风险的假设拿出来验证；
- 每一轮只做一个小实验，做完立刻看结果；
- 把文档当作辅助，不要把它当成安全保证；
- 如果代理工具本身已经有 plan mode 和任务清单，先把这些能力用足；
- 在已有大型代码库里，要特别小心重规格流程带来的拖慢；
- 如果任务很依赖界面定位和视觉反馈，要意识到文本交互会成为限制。

如果换成一句更接近开发动作的话，这篇是在提醒：**和编码代理协作时，管理不确定性的方式是拆小、验证、纠偏，不是把更多假设提前写成文档。**

## 一句话总结
这篇文章在说，Spec-Driven Development 把编码代理拉回了重规格、重前期规划的老路；更适合当下工具的做法，是把问题拆小，用自然语言驱动一轮一轮的实验和迭代。
