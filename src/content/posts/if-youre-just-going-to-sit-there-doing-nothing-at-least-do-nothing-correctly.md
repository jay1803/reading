## TL;DR
API 设计中，有时需要让某些功能“什么都不做”，但这种“无操作”也要遵循合理的方式。例如，在 Xbox 上模拟 Windows 打印 API 时，最佳做法是让 API 返回“无可用打印机”，而不是直接抛出异常。类似地，在废弃某些 API 时，可以使用“惰性（inert）”设计，即 API 保持存在但始终返回失败结果，以减少对现有代码的影响。

## 主题

### 🖨️ 处理不支持的功能：打印 API 在 Xbox 上的行为
Windows 具有打印基础设施，但 Xbox 不支持打印。如果应用在 Xbox 上调用打印 API，直接抛出 `NotSupportedException` 可能导致应用崩溃。更好的做法是让 API 表现得像打印功能仍然存在，但始终返回“没有可用的打印机”，这样应用仍然能优雅地处理用户操作（如显示空的打印机列表）。此外，安装打印机的 API 可以返回“用户取消”来防止应用试图安装不存在的打印机。

### ⚙️ 让 API 变成“惰性（inert）”以兼容现有代码
“惰性 API”指的是 API 仍然按照文档规范运行，但不会执行任何实际功能。例如，某个即将被废弃的 API 可能涉及创建、管理和关闭“widget 句柄”。错误的“惰性”实现可能让 `CreateWidget` 成功但返回 `nullptr`，或者 `EnableWidget` 接受一个看似有效但无法使用的句柄，这样会混淆开发者。正确的做法是让 `CreateWidget` 返回 `ERROR_CANCELLED`，表示用户取消创建，从而避免无效句柄的出现。

### 🛠️ 设计惰性 API 时要注意的一些细节
- **避免让 API 产生不一致的返回值**：API 的返回值应符合用户预期。例如，不应该返回 `S_OK` 却同时返回无效的数据指针。
- **利用现有的错误处理逻辑**：如果 API 早已定义了“取消”或“无效”的返回值，就应该沿用这些已有规则，而不是引入新的错误状态。
- **确保 API 文档与行为一致**：一个 API 即使什么都不做，也必须符合其原始设计的契约，以便应用能够平稳迁移或退化运行。

## 总结
在不支持某些功能或废弃 API 时，使用“惰性（inert）”设计可以保持 API 兼容性，避免程序崩溃，同时减少对现有代码的影响。
