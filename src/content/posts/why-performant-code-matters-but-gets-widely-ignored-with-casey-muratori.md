软件性能会直接影响产品成本、用户体验与市场竞争力，却常被行业用"企业客户不在乎""先做出来再优化"或"过早优化是万恶之源"等惯用说法推迟处理；Casey Muratori 的核心判断是，性能必须在架构设计阶段进入约束条件，因为上线后依靠 profiler 修补热点，往往只能改善局部，无法挽救数据布局、抽象边界和执行模型造成的系统性低效。

性能已经成为部分产品夺取市场的核心差异。传统企业软件采购通常优先考察成本、合规和功能，很少把响应速度单独列为采购标准，但 File Pilot 这类新一代文件管理器和 Blick 视频编辑器正在凭借明显更快的体验获得关注。Casey 认为，行业对性能的轻视与商业证据并不相符：领先软件公司已经反复证明，更低延迟、更高吞吐和更少硬件消耗能够改善转化率、留存与利润，只是这些收益常被组织分散在基础设施账单、用户流失和开发效率等不同指标中，没有统一归因到性能。

常见的 **profiler-driven optimization** 会运行程序、定位热点、微调代码，再检查指标是否改善，这种方法容易停在局部最优。Casey 接触过的优秀性能工程师通常先估算硬件的理论上限，例如处理器每秒能够执行多少操作、内存能提供多大带宽、目标工作负载最低需要搬运多少数据，然后持续追问实际结果为何仍与上限存在差距。这种"从硬件能力向下推导"的方法会暴露 profiler 难以指出的架构浪费：程序可能把时间均匀消耗在大量不必要的工作上，以至于没有单个热点足够突出；也可能采用了根本不适合硬件的数据结构和调用模式，局部优化再多也无法弥补。

因此，"过早优化是万恶之源"不能成为延迟思考性能的通行证。系统完成以后，工程师通常只能压缩现有热点；如果问题来自对象模型、内存布局、模块边界或数据流，真正的修复可能要求重写。设计阶段关注性能，并不意味着提前手调每条指令，而是要避免把高开销选择固化进架构。性能意识的价值恰恰在于及早识别哪些决定以后难以逆转，以及它们与目标硬件能力之间相差几个数量级。

建立这种判断力不要求会手写大量汇编，但应该能够阅读基本汇编。Casey 认为，掌握约 20 至 30 条常用指令，就足以检查一段高级语言代码最终让处理器做了什么，并辨认多余的加载、存储、分支和调用。理解现代 CPU 也可以归结为三个支柱：数据怎样通过 load/store units 和 L1–L3 caches 进出处理器；指令怎样借助 branch prediction 和 instruction cache 流过流水线；不同 operation type 如何由 execution units 调度并形成吞吐上限。掌握这三部分后，工程师面对新的 CPU 公告时，就能大致判断它对特定负载的真实提升，而不会只看厂商给出的综合数字。

Casey 对 **clean code**、TDD 等工程教条的批评也来自同一原则：任何"最佳实践"都应展示可验证的现实收益。抽象层、短函数和看似整洁的对象设计如果制造大量指针追踪、缓存失效与函数调用，代码的视觉整齐不能抵消执行成本；测试同样应接受成本收益分析。某些项目值得提前建立完整测试体系，另一些项目的生命周期、风险和迭代方式可能让少量测试甚至不写测试更合理。Casey 反对的是默认让测试驱动软件设计，因为测试结构一旦主导接口和模块边界，也可能扭曲原本更直接、更高效的实现。优秀工程师普遍具有一个特征：拒绝接受未经现实验证的编程常识，并要求每条规则给出具体收益。

游戏开发史提供了这种工程文化如何形成的案例。微软早期的 WinG 是 Chris Hecker 未经正式授权推进的内部 **Skunk Works** 项目，目标是在 Windows 上实现快速屏幕绘制；后来 DirectX 的三位创始人都曾参与 WinG 测试，DirectX 由此继承了它推动高性能图形标准化的方向。在可授权引擎出现以前，引擎本身是工作室的核心知识产权，各家公司都要自行开发渲染、寻路和工具链，Blizzard 可以把 Warcraft 1 的技术演进到 Warcraft 2，而竞争者若想制作同类游戏则必须从头开始。这种技术壁垒解释了老牌游戏工作室为何长期严密保护引擎细节。

Unity、Unreal Engine 和 Steam 的普及随后给游戏业带来了一次类似今天生成式 AI 的生产力冲击。早期阶段，低门槛工具让小团队和新开发者能够制作过去无法完成的作品；随后市场每年涌入数万款新游戏，供给增长摧毁了自然发现机制。Casey 判断，如今没有营销策略的游戏几乎不可能获得足够关注。与此同时，图形进步不再提供清晰的换代信号：1995 年的新作通常一眼就比 1990 年的作品先进，而 2026 年发行的游戏未必比九年前的产品明显更好看，新作因此还要持续与 GTA Online、Minecraft、Fortnite 等成熟旧作争夺时间。引擎降低了生产门槛，却没有降低获客难度，并使内容供给远快于注意力增长。

这种变化也是 Casey 审视 AI 编程的背景。他承认 AI 可以更快地产生输出，但自己的下一款游戏不会使用 AI，因为编程本身就是他想做的创作活动；如果目的只有获得成品，直接采用 Unreal Engine 已经能够省去大量底层工作。他把手写代码类比为手工家具：工业化工具更便宜、更高效，并不会消除少数人选择亲自制作的价值。游戏业过去的引擎普及表明，生产工具民主化最初会释放创造力，继而造成作品爆炸、发现困难和竞争加剧；AI 很可能再次放大这条曲线，也可能让只追求产量的开发者更快陷入耗竭。

贯穿这些观点的是一套统一的工程标准：先弄清硬件和市场实际允许什么，再用可测量结果检验代码、流程与行业信条。性能之所以长期遭到忽略，往往并非它缺乏商业价值，而是现代软件组织把硬件能力隐藏在层层抽象之后，又允许未经验证的工程惯例替代量化推理；重新获得性能，需要恢复从理论上限、数据移动和真实成本出发思考系统的能力。
