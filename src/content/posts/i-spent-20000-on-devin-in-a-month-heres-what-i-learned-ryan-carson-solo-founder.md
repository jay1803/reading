## TL;DR

Ryan Carson 借助 Devin 将 Untangle 的软件产能推到每天约 40 个 PR，但真正促成公司转型的不是更多代码，而是他承认消费者产品没有 product-market fit，主动走进律师事务所，发现家事律师愿意为缓解 paralegal 短缺和 divorce discovery 痛点付费。当开发执行可以被十几个云端代理并行放大后，新的瓶颈变成创始人的注意力：决定什么值得做、让不同代理各司其职，并用代码审查、风险分级、浏览器验证和 merge queue 控制质量。AI 让 solo founder 能同时承担工程、销售与客户成功，却也把 Ryan 推入近乎全天工作的高压状态，最终仍需招聘能够管理代理、验证结果并承担责任的人。

## 嘉宾背景

Ryan Carson 是 Untangle 的 solo founder。父母离异以及三个姐妹中两人经历艰难离婚，使他开始思考如何用 Large Language Models 改善离婚过程。Untangle 最初是面向消费者的 AI 产品，后来转向为 family law firms 提供服务。Ryan 此前管理和招聘过数百人，也曾在 Intel 做过一段时间的员工；目前则独自承担 Untangle 的工程、销售和客户成功，并准备招聘公司的第一位工程师。他主要使用 Devin、Codex 等代理开发和运营业务，一度单月在 Devin 上花费约 20,000 美元，之后从 Cognition 获得了同等额度的 monthly credits。

### AI 可以极大增加软件产量，却不能创造市场需求或替代产品判断

Ryan 最初认为消费者会愿意直接使用 AI 处理离婚事务，于是迅速构建并推出了 Untangle。但市场反馈否定了这个假设：按他的概括，人们在离婚时想要的是律师，而不是 AI。意识到产品没有 product-market fit 后，他没有继续依靠更快的迭代挽救原方向，而是放弃原先的消费者定位，给潜在客户发邮件，并与家事律师 Renee Bauer 进行 Google Meet。

Ryan直接询问 Renee 会把 Untangle 视为朋友还是威胁。Renee 表示律师事务所正面临 paralegal 短缺，而离婚案件中的 discovery 又是一项非常痛苦的工作，因此她不仅喜欢这个产品，也愿意支付一笔令 Ryan 满意的费用。获得第一个客户后，Ryan 又提出到对方办公室实地观察和交谈。Untangle 随之转为面向 family law firms 的 B2B 产品，并开始快速增长。

这段转型让两位说话人把代码产量与商业价值明确区分开来。主持人即使自称追求最大化 token 使用，也会有意限制功能产出，不会因为代理可以全天运行就自动寻找、实现并发布更多想法；如果某项功能被她自然搁置，她会把这种决策疲劳视为它可能不够重要的信号。Ryan 赞同 frontier model 距离判断“应该发布什么”还很远，认为所谓产品自动改进循环并不成立。主持人进一步指出，AI 增加了软件供给，却没有凭空创造愿意购买这些软件的市场。两人的共同结论是，创始人仍需离开屏幕、接触真实客户，并只构建市场确实需要的东西。

### 当执行能力趋近无限时，创始人的核心技能变成管理代理并保护稀缺的注意力

Ryan 从 Cursor、AMP 等需要人在本机持续参与的工具转向 Devin，是因为云端代理可以在他离开电脑时继续处理 bug、数据查询和快速 PR。他认为未来工程工作会主要发生在 cloud agents 上，虽然本地开发仍会保留一部分作用。他目前几乎“住在 Devin 里”，通常同时运行 10 到 15 个线程；但人一次只能真正跟踪四五项任务，因此解除机器端的执行限制后，人的认知容量立即成了瓶颈。

他的应对方式是给 Devin 线程分桶：bugs 用于需要较快处理、但未必属于最高优先级的问题；P0 放无论当天如何分心都必须推动的业务事项；其后还有 P1、P2、新功能和投资者相关工作。为了避免被八块屏幕和大量并发任务牵走注意力，他同时使用 UG Monk 的纸质待办系统，把一周最重要的事项写在纸上。云端代理让他能够在手机上随时工作，但代价是工作时间可能扩展到一天 21 小时，并带来持续的决策疲劳。

主持人采用另一种分桶方式：她不主要整理任务，而是切分自己的时间，一部分用于与 AI 紧密协作，一部分集中启动任务或检查后台代理。尽管具体方法不同，两人都认为，已有的组织管理经验正在成为 AI 工作的关键优势，包括如何设计结构、分配职责、确定优先级、委派工作，以及判断何时需要微观介入、何时应该放手。代理数量可以继续增加，但创始人的注意力不能同比扩张，因此管理代理的核心不是让它们始终满负荷运行，而是让有限的人类判断集中在最重要的少数事项上。

### 编码代理的真正价值在于成为理解代码与业务的通用运营代理

Ryan 和主持人都反对把 Devin 一类工具仅仅看作写产品代码的代理。主持人的判断标准是：如果一个“员工”既理解整个 codebase，又能按需编写工具解决业务中的任何问题，还能持续在后台工作，那么它自然可以进入报价、运营、文档和客户分诊。她已经让 Devin 运行 Deal Desk、制作定制报价，并处理多种非工程事务，因此认为工程师以外的职能也应该直接使用 cloud agents。

Ryan 的 Watchdog playbook 展示了这种能力如何进入日常运营。随着 Untangle 服务越来越多律师事务所及其案件，他一个人同时负责 customer success、工程和销售，已经无法手动掌握每个账户发生了什么。Watchdog 会针对每家事务所重复执行一套 skill，检查上次运行以来的活动、客户遇到的 UX 问题和 Sentry errors，再对结果进行转换、过滤和排序，而不是简单倾倒原始数据。

Watchdog 最终只向 Ryan 提交最重要的三个问题，并进一步核查每个问题是否已经修复、是否正在处理中，或是否存在一个迟迟没有合并的 PR。由于 Untangle 每天可能发布约 40 个 PR，仅仅发现异常并不够，代理还必须理解当前修复状态。Ryan 会在同一线程中继续追问最值得深入的问题。类似的 playbook 也被用于整理业务信息和起草 investor updates；对他而言，价值不只是自动完成某次任务，而是把反复出现的经营需求固化成可重复运行、能够观察整个公司的运营机制。

### 代理产能越高，质量控制越需要从人工逐项审查升级为分层的验证系统

每天产生大量 PR 后，人不可能沿用传统方式逐项深入审查。主持人的 Merge Mommy 会在 PR 通过包括 BugBot 在内的 CI checks 后启动，从 blast radius、安全性等约五个维度评估风险。低风险 PR 会自动获得批准并可直接合并；中高风险 PR 则在 Slack 中通知她或同事进行人工审查。这一机制既帮助团队清理 PR 队列，也满足其 SOC 2 controls 对替代性审查的要求。

Ryan 的 Land PR playbook 采用另一条控制链。代理完成 PR 后，它会触发一次全新的 Devin Review，处理审查意见，并允许最多两轮“发现问题—修复—再次审查”的循环。随后 Devin 必须在浏览器中执行功能流程，录制带旁白、字幕和红绿测试清单的视频。Ryan 不再重新检查所有实现细节，而是观看这份验证证据；只有在他说出“video approved”之后，代理才能合并 PR。GitHub merge queue 再负责维持大量并发改动下的合并秩序。

两套做法都把人的介入从全面审查改为风险与证据驱动的审批：自动系统先发现代码问题、限制修复循环、判断改动风险并执行用户流程，人只处理高风险变更或批准关键验证结果。Ryan 因此认为，AI 提高开发吞吐量后，团队反而必须更擅长 CI/CD 和 DevOps，而不是降低对它们的重视。主持人也提醒这种验证并非始终可靠：她只能偶尔让 Devin 完成视频验证，前端任务有时会耗尽 session credits 后失败，截图功能也只是间歇可用。

### 成熟的代理工作流依赖明确分工，而不是寻找一个包办所有工作的模型

Ryan 主要把 Devin 当作云端工作环境，用于并行工程任务、快速修复、业务查询和持续运营；主持人也把 background agents 用于 bug auto-fix、客户通话中临时提出的 MCP、一次性任务和运营工作。它们的优势在于能够脱离人的本机持续执行，但并不适合所有需要高频反馈的任务。

需要人持续介入的大型功能、跨前后端开发、长期重构和前端体验调整，则更多交给本地 Codex。两人都看重它的低延迟、较充裕的 token、subagents，以及与本机浏览器配合的能力。主持人会让 Codex 先写 user stories，再打开 preview branch，以用户身份逐条执行流程、标记通过项、发现 bug，并循环修复到验证完成。Ryan同样认为，当一个 UI 密集型功能需要代理长时间“grind”，同时又需要自己偶尔收窄方向时，Codex 的互动体验难以替代。

设计任务又被进一步拆开。两人都认为 Claude Design 擅长从参考网站或 Figma 中分解出可复用的 design tokens、design.md 和设计文件，但不擅长凭空创造新设计；Ryan 还认为 Devin 的设计能力很差，而 Codex 也不擅长最初的设计抽象。主持人的流程因此是先由 Claude Design 提炼视觉系统，再把 design.md、设计文件和 Figma 内容交给 Codex，让它建立技术设计系统、shared components 和 monorepo 中的关联结构；她还尝试让 Codex 通过 Figma plugin 把 design tokens 重新写回 Figma。PR 审查、风险评估和邮件管理则分别交给 BugBot、Merge Mommy、OpenClaw 或 Codex。整套实践强调的是按任务的自治程度、反馈速度、专业能力和验证方式分工，再把结果衔接起来，而不是期待某个模型包办全部工作。

### AI 时代的协作系统必须让对话贴近执行上下文，并减少不能产生行动的沟通

Ryan 几乎不使用 Slack，计划随着 Untangle 招人，把多人项目讨论直接放进相关 Devin 线程。这样，需求、讨论、代理执行和验证都留在同一上下文中，团队无需反复判断信息究竟在 Devin、Slack 还是 Google Docs。他还考虑禁止一对一文字聊天：真正私密的事项可以通话，其余工作则应公开并贴近执行位置。他在 Intel 做员工时的体验是，组织里有大量无关紧要、又不能让参与者采取行动的讨论；代理最终仍需要这些讨论中的上下文，因此不如从一开始就在工作发生的地方交流。

主持人偏爱 Slack，并不是因为 Slack 中的 Devin 功能明显优于 web app，而是因为公开线程具有组织教育作用。她在 LaunchDarkly 推广 background agents 时，把 Devin 放进公开 Slack channels，使团队第一次能够实时看到公开进行的编码工作。其他人可以观察 AI 能做什么、学习如何与它协作，也能在 multiplayer thread 中共同参与而不彼此干扰，因此公开的代理工作本身成为推动组织采用 AI 的方式。

两人的分歧主要在承载对话的界面，而非协作原则。主持人认为人类不会停止使用 chat，但组织可能需要摆脱 DM、private channel 和无结果闲聊构成的“Slack culture”；理想情况下，每个线程都应推动一项工作。Ryan 则更进一步，希望让沟通直接进入代理即将执行任务的上下文。双方都反对把决定和信息锁在私聊或孤立文档里，也都要求协作最终转化为行动，而不只是增加交流量。

### AI 没有消除对人的需求，却把工程人才的核心能力改写为代理管理与结果验证

AI 让 Ryan 以 solo founder 身份同时推进产品、工程、销售和 customer success，并快速把 Untangle 带到增长阶段，但这种杠杆没有消除人的容量限制。他形容自己处于 “Max Q”——压力已经达到必须招聘的程度。能够随时从手机向代理提供反馈，使他被工作覆盖到一天约 21 小时；更多执行能力没有减轻负担，反而产生更多需要排序、检查和负责的结果。Ryan 与主持人都曾强调 solo founder 模式，如今却都准备招聘真人来扩展组织容量。

Ryan 正在招聘 Untangle 的第一位工程师，并把筛选重点从面试表现转向实际代理管理能力。候选人第一阶段无需先与他见面，而是录制完整桌面，展示自己如何为一个已有应用开发新功能。Ryan 希望看到整个过程，而不先受“是否喜欢这个人”的印象影响；收到的视频让他能够观察候选人如何拆解任务、指挥代理、介入执行并检查结果。

进入第二阶段的候选人会获得 Devin 权限，在真实环境中完成实际任务，并继续留下过程录像；Devin 本身的 computer replay 也能补充执行记录。Ryan 计划在最后进行简短交流，然后根据实际产出与代理工作过程做出招聘决定，入职后也主要通过 agent output 管理工程师。主持人将其概括为一种针对人的 verification loop：未来工程师的关键能力不只是亲自写多少代码，而是能否让代理完成真实工作，并证明结果确实可用。

### 提到但未深入展开的话题

访谈还简短涉及 WorkOS 与 Jira 的赞助内容、Ryan 与三个姐妹的关系及创建 Untangle 的家庭动机、Cognition 提供的 Devin credits、UG Monk 纸质待办系统与八屏工作环境、GitHub merge queue、BugBot、Merge Mommy、Cursor、GroqBot、Eve 和各类具体工具体验。两人也谈到对 Claude 与 Opus 5 输出风格的主观不适、Claude 在 cybersecurity 和设计等特定任务中的优势、Polly 与 OpenClaw、Mac mini，以及 Codex 帮主持人处理 Gmail 中约 2,000 封未读邮件。结尾还提到 Ryan 在 X 上发布招聘信息、Untangle 的招聘入口、How I AI 的订阅与社交媒体宣传。
