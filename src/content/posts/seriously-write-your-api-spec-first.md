## TL;DR
作者主张 API 应该 spec-first：先把 OpenAPI 规格当成对消费者的明确契约，再去写实现。这样做的价值不只是“文档更完整”，而是把接口体验、变更边界、协作方式、测试路径和后续维护都提前设计好，避免代码先行后再倒推规格所带来的混乱、歧义和信任流失。

## 关键洞察
文章从一次糟糕的 Twitter/X API 集成体验讲起：文档冗长却不清楚，Postman workspace 一年没维护，示例代码还停留在已经废弃的旧版本。结果是开发者迅速失去信任，干脆放弃集成。作者借这个例子强调，API 使用者对生产者的判断，很大程度来自接口是否清晰、是否稳定、是否在功能上线时就配好可依赖的说明与约束；一旦开发团队把“先把功能做出来”置于开发者体验之前，消费者感受到的就是自己并不被重视。

接着作者区分“大家都承认 OpenAPI 规格有价值”和“真正从规格开始开发”之间的差别。很多团队会在代码完成后再生成 spec，这样虽然也能得到一份对现状的描述，但那更像事后记录，不是事前承诺。作者要的是 API-first：先认真定义 endpoints、请求与响应、参数、schema，以及什么样的体验会让集成方顺手，再让实现去服从这个设计。这样做的核心不是形式，而是 intentionality——你在写第一行代码前，就已经决定要给消费者一个怎样的接口、怎样的文档、怎样的演进边界，因此新功能一上线就天然有文档，破坏性变更也更容易在设计阶段被消灭，而不是等消费者踩坑后才补救。

房屋蓝图的比喻把两种方法的差异说得很直白：先画蓝图再盖房子，和先把房子盖出来再补一张蓝图，最终都能得到“房屋 + 图纸”，但前者通常更合理、更顺、更接近真正需求；后者虽然也能住，却更像把已经发生的偶然结果整理成说明书。作者认为 code-first 生成的 spec 常常就处在这个位置：它可以描述系统，却未必代表系统是按最清晰、最友好、最可维护的方式被设计出来的。

在具体收益上，文章列了六点。第一，清晰度与一致性更高，因为团队一开始就围绕同一份规格工作，减少猜测。第二，错误更早暴露：当行为和要求先被写清楚，潜在问题会在实现前出现，甚至可以先做端到端测试；作者特别提到 Postman mock server，可以根据 spec 先返回模拟响应，让测试流先跑起来，后面再把 mocked endpoint 替换成真实实现。第三，协作更顺，因为规格成了开发、测试、利益相关方共同讨论的对象，大家能在开工前把疑问和分歧摊开；Postman 也支持直接围绕 spec 留评论和提问题。第四，集成更平滑，尤其在 AWS 场景下，可以借助 OpenAPI 扩展把 mock 快速连到真实服务，甚至通过规格把 endpoint 直接接到 AWS 服务。第五，时间上反而更省：把规划工作前置，会减少后续开发、测试和 debug 的来回返工，因此更快交付高质量软件。第六，文档天然更有意义，因为路径、schema、参数的说明本来就在 spec 里，只要规格写得清楚，集成方理解成本就会明显下降。

作者也给了一个有限让步：code-first 并非“错误”，很多团队确实靠它做成了事，自己只是立场很强，认为这仍不是长期最优路径。这个判断来自他的亲身经历——在组织内部推动“先写 API spec 再写代码”并不轻松，也不容易说服别人，但一旦推进下去，团队会更尊重开发者体验与 API 设计，也会发现很多面向消费者的清晰性，最后同样会让内部实现更简单。

最后落到行动建议：如果要开始 spec-first，就亲手从零写一份规格。作者推荐 Swagger Editor，因为它会边写边渲染，让人直接看到 schema、endpoint 和复用方式如何落地。重点不是换个文档工具，而是训练自己先定义数据传输模型与接口契约，再进入编码。作者把这种方式视为与传统写代码习惯截然不同的一套工作流，但认为它更适合追求 API 的长期可维护性与长期可用性。

## 一句话总结
把 API 规格放在代码前面，本质上是在把“接口契约、消费者体验和演进约束”前置为设计对象；这会让 API 更清楚、更稳定、更容易协作与测试，也更值得被外部开发者信任。
