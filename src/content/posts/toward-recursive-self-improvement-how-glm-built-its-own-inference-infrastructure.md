GLM 参与构建自身推理基础设施的关键突破，是在可定位原因、可快速验证的反馈闭环中，把模型的编码能力转化为持续的系统优化能力；这已形成递归自我改进的早期形态，但目标选择、系统边界和风险判断仍由人类掌握。Z.ai 报告，GLM-5.3 驱动的 Infra Agent 与工程师协作，在不到两周内完成 GLM-5.3-Flash 从初始适配到生产上线的过程，将端到端吞吐量提高至初始基线的约三倍，部署环境覆盖超过 10 万张国产 AI 加速卡。

这次工作发生在 GLM 从内部试用工具变成日常工程伙伴的过程中。团队坦言，GLM-4.7 之前使用自家模型编程还带有支持自家产品的义务感，到了 GLM-5.3，模型已成为不可或缺的开发工具。能力外溢也带来治理压力：团队自 2025 年 10 月开始强化网络安全能力后，安全合作伙伴在不到一年内利用 GLM 发现了真实代码库中的数千个漏洞，促使团队建立可信访问计划。如今，模型开始直接改进承载 AI 的基础设施，进一步触及“自主设计和训练下一代模型”的 Recursive Self-Improvement（RSI）路径，但当前成果尚未达到完全自主的程度。

GLM-5.3-Flash 的部署同时受到硬件和软件生态约束：国产加速卡的显存容量与带宽有限，集群规模缺乏既有部署经验，还要支持新模型架构、1M-token 上下文窗口和多模态请求；kernel 支持与文档也不完善。团队采用计算换带宽、通信换显存的策略，组合了 linear attention 与 LM Head 的节点内 Tensor Parallelism、ReplaySSM、W8A8 量化、INT8/FP8/BF16 混合精度缓存量化、Layer Split，以及 Encode-Prefill-Decode（EPD）分离架构。文章称，最终系统的硬件利用效率和单 token 成本达到主流 NVIDIA GPU 的可比水平，并承载了 GLM-5.3-Flash 的全部生产推理。模型以 Ox-Alpha 的匿名名称在 OpenCode 和 OpenRouter 上接受真实使用测试，上线一周内成为两个平台使用量最高的模型，六天处理超过 62 万亿 tokens。

复杂推理系统的优化难点在于，端到端指标能够暴露退步，却无法直接解释原因。数值测试失败、首 token 延迟上升 30%、输出吞吐量下降 20%，背后可能涉及 kernel、并行切分、通信、显存管理或服务调度之间的动态交互。即使 Agent 理解整个代码库，也仍需判断问题发生在哪一层、当前假设错在哪里、下一步应做什么实验。传统工程师依赖经验串联压测、日志、profiling 和微基准；要让 Agent 连续执行这套诊断过程，就必须把分散的工具组织成可直接调用、可重复运行的工作流。

团队将这种环境称为 **dense feedback**：反馈应足够局部，能关联到具体 kernel、输入形状、线程、执行区间、代码路径或修改；获取成本应足够低，让局部问题通过 kernel 测试或微基准及时得到答案；结论还必须接受参考实现、对照实验和可比指标的客观检验。运行时相关性只能指引调查，不能独自确立根因。正确性测试回答计算是否准确，执行轨迹说明时间花在哪里，性能实验检验方案在什么条件下有效；局部验证负责提前淘汰错误修改，端到端测试负责确认收益能否迁移到真实负载，并排查新回归。

数值正确性案例说明，反馈环境首先要定义完整的测试对象。团队建立了推理引擎并行策略到 kernel 实现的映射，将部署配置转化为输入切分、执行路径和结果合并的具体检查项，再对齐计算语义与输出位置，比较切分和未切分路径的误差。这个过程发现 KDA kernel 的 Context Parallelism（CP）路径存在精度问题：跨上下文分片合并状态变换、更新下一分片初始状态时，两处 tl.dot 即使输入为 FP32，也默认使用 TF32 计算，误差随长上下文累积。Agent 将两处运算显式设为 input_precision="tf32x3"，通过三次 TF32 Tensor Core 运算提高精度，同时尽量保留性能优势。修复经过回归验证，并已合入 Flash Linear Attention 的 PR #1180；局部通过后，仍需回到目标部署检查模型级精度和服务性能。

并发瓶颈案例则从明确的性能约束逐层追到 Python/C++ 边界。工程师分别设置 Prefill、Prefill + KV Transfer、Decode 测试，要求相同负载下加入 KV Transfer 后的性能损失不超过 5%，Agent 却发现部分场景超过 20%。时间线显示，Python 侧 KV Transfer 与 DeepEP dispatch/combine 调用区间完全没有重叠。继续检查发现，使用中的 DeepEP v1.2.1 没有在 intranode_dispatch 和 intranode_combine 中显式释放 Python GIL，其中 dispatch 还会在 CPU 上等待 GPU 返回接收 token 数。锁被持有期间，同一进程中的 Mooncake Transfer Python 线程无法及时提交传输任务，底层异步传输能力因此无法充分发挥。同版本的 internode_dispatch 已释放 GIL，并注明是为了避免阻塞其他线程的 KV Transfer，提供了直接对照。修复相关 C++ 执行区间的 GIL 释放后，团队同时检查时间线与原始性能指标，确认相同条件下的性能损失降至 1% 以下。

kernel 性能优化还要求 Agent 学会判断局部提速的系统代价。计算 kernel 占用更多资源，可能挤压 KV Transfer，使整体流水线变慢，因此单个 kernel 延迟不能充当唯一目标。团队让 Agent 从 SGLang、Flash Linear Attention、DeepGEMM 等项目中提取跨代码库、语言和硬件的优化经验，通过增量与消融实验整理成“优化骨架”，记录适用条件、变换方法、资源约束和验证证据。面对新 kernel，Agent 以这些骨架提出候选方案，再根据 profiling 和分层测试调整 tiling、访存和资源分配；经过验证的经验继续回流骨架库。

一个 KDA Decode kernel 展示了这种经验积累如何产生实际收益。引入 ReplaySSM，以额外计算换取显存节省后，kernel 执行时间首先上升；Agent 随后的除法优化将这一版本的执行时间降低 9.6%。当反馈进一步指向计算瓶颈时，Agent 发现沿 V 维度切分的实现把相同的 FP32 归一化和 gating 计算重复执行了四次，于是将这些 tiles 合并到一个 thread block，把共享中间结果保留在寄存器中，并用一次 warp-level reduction 消除重复计算。这个方案牺牲部分并行度，换来相对上一版本 1.71 倍的加速，说明优化方向必须由实际瓶颈决定，增加并行度并不必然提高性能。

这些结果依赖清晰的人机分工：工程师定义目标与约束，建设 Agent 可使用的反馈环境，并审查数值语义、异步并发、系统架构和生产风险；Agent 负责分析、提出假设、修改代码和运行实验，再根据证据保留、修正或放弃方案。大量无结构日志会掩盖信号，不完整的 profiling 会误导归因，微基准收益也可能在真实服务中消失，因此正确性、稳定性和端到端性能必须共同构成验收标准。GLM 优化运行自身的系统，系统再支持 GLM 提供服务，这个循环已经成立；通往更强自我改进能力的工程基础，是让每一轮修改都产生可归因、可复验、能指导下一轮行动的证据。
