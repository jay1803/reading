AI 让代码产能迅速扩张后，软件交付的核心瓶颈已经从生成代码转向验证代码；**Harness Engineering** 的作用，就是把团队标准编译进代码仓库，让每项变更都受边界约束、经过强制检查、留下可追溯证据，从而把"看起来合理的 AI 代码"转化为可信软件。把规范写进 context file、style guide、wiki 或 prompt 并不足够，因为模型会把自然语言指令当作可偏离的建议，也无法像工程师那样长期记住 review comment 和口头纠正；代理真正无法绕过、并且能跨会话积累经验的地方只有 repository。模型提供交付能力，harness 则提供可观察的问责机制，使任何模型、代理或人员提交的变更都能回答：做了什么、依据哪条规则、产生了什么结果。

"Harness Engineering"这一名称自 2026 年 2 月开始进入行业讨论，Thoughtworks、LangChain 等机构随后围绕相近问题形成方法论，因为大量 AI pilot 虽然演示出色，却在进入生产环境时停滞。代码生成能力早已足够强，真正限制规模化应用的是团队无法以同样速度判断生成结果能否信任；积压的"貌似正确但未经验证"的变更并不构成交付速度，而是等待出故障的库存和技术债。与此同时，个人开发者已经在运行夜间自动接单、编码、验证和汇报的软件工厂，Ramp、Stripe、DoorDash 等企业也建立了内部版本，市场上甚至出现了现成平台。模型访问权和通用平台可以买到，但企业自己的 harness 无法直接采购，因为它必须把该组织特有的质量标准、权限边界和风险偏好落实到自己的仓库中。

团队把工作交给 AI 通常经历四个成熟阶段。**Assisted** 阶段由模型提出建议，人阅读代码并决定是否发布；**Harnessed** 阶段允许系统执行多步骤任务，人根据系统留下的证据审批结果；**Risk-tiered** 阶段由 gate 判断风险，低风险变更可以自动合并，人只审核高风险事项的意图；**Autonomous** 阶段则由 harness 接收、执行并验证工作，人负责治理边界、审计证据，并在系统越界时介入。随着自动化范围扩大，人的检查点逐渐从逐行查看 diff，上移到审核证据、判断高风险意图，最终集中于制定规则和监督边界；人始终存在于更大的工作闭环中，而部分 review、challenge 和 reflection 也可以变成受治理的机器工作。

成熟实现普遍依赖三个并不复杂的模式，第一个是**失败即关闭的 gate**。最基础的 gate 就是 repository host 上的 required check：无法产出规定证据的变更不得合并，无论提交者是资深工程师还是凌晨三点运行的代理。更成熟的系统连读取 gate 状态的组件也不预设为可靠，例如合并程序主动向仓库平台查询所有 required checks，查询过程本身一旦出错就按失败处理。基础设施故障、运行中触及预算上限等情况同样必须让工作停止，且预算触发的停机不能靠自动重试自行恢复；静默降级既会摧毁信任，也可能让成本快速失控。

第二个模式是把**证据作为工作流的通货**。每个合并变更都应在账本中留下检查项目、检查主体和检查结果，成熟 harness 还会在 pull request 中附加可复现清单，记录编写代码时所用的模型、prompt 和配置，让数月后的 root cause analysis 能直接查明变更来源。review 因此逐渐从阅读每一个 diff 转向审计验证结论，并在证据薄弱或风险较高的地方深度抽样，质量标准仍然保持，只是人的工作层级被抬高。验证还必须具备独立性：如果同一条推理路径既创作变更又定义证明条件，得到的很可能只是同一个判断扮演两个角色；reviewer 应拥有独立于 author 的职责、证据或目标，使用不同模型家族担任 judge 也能减少双方共享盲点、以相同方式失败的概率。

第三个模式是把过去二十年形成的优秀工程纪律"编译"为仓库配置。测试优先、小型 diff、可执行的验收条件和可追溯变更，需要从依赖团队文化和 wiki 记忆，转化为 hook、required check 与版本化 ruleset。作者自己的软件工厂把"test before commit"设为硬规则，只要测试失败，hook 就禁止代理宣称任务完成；branch protection 也以可版本控制的规则表达，避免仓库级静态文档逐渐过时。harness 的成熟度并不取决于采用多少新奇组件，而取决于有多少工程纪律已经成为任何参与者都无法跳过的强制条件。

长期运行软件工厂后，操作者的工作也会发生变化：最初是一条指令对应一个 diff，随后转向给整个系统设定意图、边界和可接受结果，由工厂完成执行并留下证据，而证据又反过来改变下一轮需求。随着这些反馈积累，系统会逐渐区分"工作应当如何完成"与"最终软件必须满足什么条件"，甚至形成最初没有人为预先设计的组织结构。这相当于让仓库反向运行 **Conway's Law**：当标准、证据和判断机制被充分写入软件，组织角色也会在仓库内部成形。

这些角色可以包括负责把意图整理成合格任务的 product seat，以及分别攻击可行性、安全性和用户体验的 quality review seats；每个角色都留下不可跳过、可审计的决策记录，immutable ledger 还能持续追踪各 reviewer 的判断是否经得起后续检验，并按照组织的风险容忍度校准 judge。只有当某个角色的输出能够被机械验证时，它才适合交给 autonomous agent；若验证本身依赖复杂判断，该席位仍应由人承担。作者称其研究系统 HydraFlow 已经让 repository 在设计落地前召集 review council、具名记录异议，并保存对 judge 的校准历史。

作者把这套治理结构压缩为 **PAAA**：**Purpose** 说明工作为何存在，**Articles** 规定始终必须为真的条件，**Actors** 在被授予的权限内执行工作，**Artifacts** 保存产出、证据、决策记录、账本和制度记忆。harness 让 Articles 可执行，人和代理共同担任 Actors，证据与记忆沉淀为 Artifacts，而业务意图提供 Purpose；失败产生的新证据还会反馈并修改规则，形成使命制定规则、规则约束执行、执行留下记录、记录推动制度演化的闭环。当仓库同时拥有权限、边界、证据、记忆以及修改自身规则的机制时，它已经接近一个可运行的工程组织：人负责定义目的、授予权力、批准根本规则并审计系统，代理则在这些制度内扩大执行能力。

因此，投资 harness 最终建设的并非一条更聪明的自动化流水线，而是一套受领导层治理、能够自证其行为合法性的"盒装开发组织"。企业可以用 PAAA 做现实审计：谁为 AI 项目设定方向，方向缺失时系统如何停下；哪些条件必须跨仓库和工作流持续成立，无人监督时由什么机制强制执行；每个决策角色由谁承担，角色失控时如何发现；系统保存哪些记忆，这些记忆具体存放在哪里。AI 软件工厂能否从高产原型走向可信生产，最终取决于组织能否把这些问题的答案变成仓库中可执行、可审计、可演化的制度。
