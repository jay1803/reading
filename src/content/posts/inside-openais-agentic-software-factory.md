Codex 已成为 OpenAI 的工作底座，也正在把软件开发从人逐步操作工具的流程，改造成由人确定目标、代理执行并持续接收生产反馈的循环。工程师之外，财务、招聘、法务等团队在四个月内从几乎无人使用 Codex，增长到约 90% 使用；如今几乎所有员工每周都会使用 Codex 和 ChatGPT Work。这个转变没有来自管理层的强制要求：即使早期 Mac 版 Codex 会把代码直接展示在屏幕上，非技术员工仍用它完成调研、演示文稿、文档和表格。OpenAI 内部版本之所以尤其有用，是因为它接入了公司大量系统，而各团队又通过面向具体岗位的 skills 和 plugins，把通用代理变成自己的工作工具。

使用率跃升还依赖代理能把复杂任务做到底。Codex 的 `/goal` 允许员工设定目标后让它持续工作；随着长任务的执行能力改善，使用率在四月至五月间从 60% 升至 90%。一个任务线程可以延续数天，代理还会派生其他代理处理子任务，减少人需要同时管理的工作界面。Codex 团队认为，目前既有产品终于释放模型能力的变化，也有员工对现有能力认知不足的"awareness gap"：有人已用它监控 Slack、更新 Airtable、制作入职材料，其他人则靠同事口耳相传才发现这些用途。随着 ChatGPT Work 进入更多专业领域，产品工程团队也开始吸纳领域专家，由他们判断一份幻灯片、电子表格或商业报告究竟好在哪里。Codex 和 Work 已经重要到轻微故障也会立刻引发内部员工报告，有时甚至早于自动告警。

这股变化首先冲击开发工具和交付容量。OpenAI 在 2025 年底曾犹豫是否要推出介于终端 CLI 与完整 IDE 之间的 Codex 桌面应用，也考虑过像 Antigravity 那样基于 VS Code 开发；团队最终押注代理越强，IDE 越不重要。自 2026 年一月 Codex 使用量上升以来，公司内 IDE 使用量下降，不过 Codex 应用六月也加入了文件编辑能力。与此同时，每位工程师提交的 pull request 数量快速增长，部分版本控制、构建、测试和部署系统的负载约在六个月内增加了十倍。代码生成越快，越需要重想 PR、代码审查和 CI/CD 的容量与形式；原生移动应用尤其受制于 Apple 和 Google 耗时数小时至数天的审核流程，生成代码的速度无法直接转化为用户拿到更新的速度。

OpenAI 的**代理式软件工厂**以人定义结果开始，而非让代理自行决定什么值得做。工程师或产品经理确定问题、优先级和期望结果，Codex 再从代码仓库、GitHub、Slack、Notion、Databricks、Datadog、内部日志及公司 skills 中收集上下文。OpenAI 还把文档移进源码，使代理更容易理解代码；新工程师入职时也会被建议先向 Codex 提问。代理随后实现改动、运行构建和测试、修复失败，提交 PR，并继续处理 CI 中更完整的检查，直到结果通过。对可能影响性能的 PR，额外的 perf harness 会将其送进 Synthetics A/B 框架评估。

审查阶段不再只依赖一个通用 AI reviewer，而是让多个带有领域配置的代理分别检查变更，例如从云基础设施或安全角度寻找问题。这种专门化的价值取决于代理能否读取相应代码、文档和实践，并将有限的上下文集中在自己的领域。改动还会按风险分流：高风险变更可能需要更多代理审查或最终的人类审核；选择加入相应机制的代码区域，可以由代理自动批准低风险 PR。合规意见也能按需交给专门代理或人处理。提交代码的代理则继续跟进审查意见并修改 PR，以免把不断增加的提交量全部转嫁给人工审查者。

变更获人批准进入生产后，会交给另一个代理"护送"至完整、安全地上线。它可以读取代码以定位 feature flag，理解改动及成败信号，自建针对这次变更的监控面板，并观察相关生产指标。监控粒度因此从工程师维护的服务级 dashboard，延伸到每次部署。生产数据又反过来触发开发：Perf Factory 用代理整理告警和面板、去重、识别真实的延迟回归、追查原因并提出修复方案。故障时，基于 Codex 的 Sevbot 会收集上下文、提出缓解选项并在 Slack 回答工程师的问题，但目前不会自行执行缓解措施；工程师可以明确指示它采取某项行动。让它自主处理部分常规故障、避免夜间叫醒值班人员，仍是目标而非现状。

这套工厂把人的工作进一步推向目标选择、风险判断和生产授权，也让代码生成之后的审查、交付、移动端发布及事故处置成为新的速度边界。代理已经能贯穿从实现到生产反馈的多数环节，但 OpenAI 仍在依据变更风险和实际运行后果，决定哪些环节可以自动放行。
