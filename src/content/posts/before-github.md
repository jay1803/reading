## TL;DR
GitHub 最大的历史价值不是代码托管本身，而是把开源项目的“社会记忆”集中成可发现、可检索、可追溯的公共档案；如果 GitHub 继续产品漂移、社区信任下滑，开源世界回到多中心是健康的，但必须补上一层独立、长期、无聊且有资金保障的公共档案系统，否则会重演旧 Web 的消失问题。

## 核心主张拆解
- GitHub 曾经把开源的发布、发现、协作、issue、PR、release、wiki、CI、API、webhook 和组织页面压缩成一个默认场所，显著降低了参与门槛，也让大量项目获得用户、贡献者和职业网络。
- 这种中心化有副作用，却创造了一个意外的公共图书馆：废弃项目、fork、旧 issue、讨论和发布记录仍然可找；相比早期个人服务器、Trac、Subversion、SourceForge、Bitbucket 和自建站点，GitHub 保存了更多上下文。
- GitHub 同时放大了微依赖生态：GitHub + npm 让创建、发布、发现、安装、依赖小包几乎无摩擦，项目数量爆炸，包图增长速度超过人类理解能力。
- 早期开源世界的摩擦迫使开发者审慎选择依赖：项目通常有历史、维护者、网站、release 流程、社区声誉和更高迁移成本；现在的低摩擦生态把 GitHub 变成供应链信任层的一部分。
- 当 GitHub 的社区信任下降，问题不只影响源码托管，还会影响 npm trusted publishing、许可证判断、维护者可见性、issue 历史和依赖选择文化。

## GitHub 正在失去什么
- 文章认为 GitHub 的衰退来自不稳定、产品 churn、Copilot/AI 噪音、领导层不清晰，以及平台不再围绕原本创造其价值的开源社区设计。
- Mitchell Hashimoto 宣布 Ghostty 将离开 GitHub，是作者眼中的强信号；Zig、Strudel、Tenacity 等项目迁往 Codeberg，说明“离开 GitHub”已不只是象征姿态。
- Git 本来适合多中心世界；分布式版本控制获胜后，全世界却标准化在一个巨型中心化服务上，这是现代开源的核心讽刺。

## 分散化的代价
- 多 forge、多服务器、多小社区可以恢复自治，降低对 Microsoft 产品选择和管理层状态的依赖，也能让不同社区选择更适合维护者的工作流。
- 代价是“代码可分布”不等于“社会上下文可保存”：issue、review、设计讨论、release notes、安全公告、旧 tarball 和维护者决策脉络比 Git 仓库本身更脆弱。
- 早期 Web 的教训很直接：个人域名过期、VPS 关停、开发者离世，包文件和项目主页就会消失；PyPI 上仍有元数据，但实际文件可能早已不可得。

## 需要的新基础设施
- 作者希望出现一个公共、无聊、资金充足的开源档案机构，依靠 endowment 或公共资助长期保存源码、release artifact、元数据和足够的项目上下文。
- 这个档案不需要赢得开发者生产力市场，也不需要成为下一个 GitHub；它的职责是让重要软件遗产不依赖某家公司商业模式、领导层心情或增长战略。
- 下一代开源基础设施应让项目更容易迁移、更容易镜像社会上下文、更容易保存 release，并让单一公司的产品漂移更难演化成整个文化的危机。

## 证据薄弱处
- “GitHub is slowly dying”更多依赖作者体感与若干高信号迁移案例，缺少量化指标，例如活跃仓库迁移率、PR/issue 活跃度变化、核心项目托管分布、开发者信任调查。
- 作者对公共档案的治理、资金来源、法律责任、隐私/删除权、恶意代码保存边界、跨 forge 标准化成本展开不多；这是方案最难落地的部分。

## 收束
开源接下来可能会重新分散，但真正该保留的是 GitHub 时代积累出的可发现记忆；如果只恢复自治而不建设档案层，开源会得到更多自由，也重新承担更多遗忘。
