Vim 让用户拥有与插件作者同等的编辑器控制权，VSCode 让用户消费专业开发者提供的扩展，但对大多数开发者，后者带来的便利与可靠性更值得优先选择。Hillel Wayne 在加入 Antithesis 担任 Developer Educator 后，需要从 Windows 转向公司统一使用的 NixOS，于是暂时放下惯用的约 2000 行 Neovim 配置。这次迁移让他重新审视：自己为什么需要如此庞大的配置，以及这种控制欲究竟换来了什么。

两种编辑器的差异，从把 Ctrl+N 设为保存文件就能看出来。在 VSCode 中，用户在 keybindings.json 里把按键关联到内置命令 workbench.action.files.save；在 Neovim 中，用户可以把它绑定到一个调用 vim.cmd.write() 的任意函数。前者通过静态数据选择已有能力，后者执行代码、直接改变正在运行的编辑器状态，甚至无需修改配置文件，在命令行里就能临时新增映射。Vim 的传统按键映射还可以表示"执行输入 :w 并回车所产生的效果"，其结果会受到其他映射影响：如果冒号键被重新映射为 o，原本用于保存的操作就可能变成新建一行并输入 w。用户因此能让 ;r 粘贴剪贴板、为 normal mode 和 insert mode 使用不同设置，乃至让保存文件的行为随满月发生变化。

这种可编程性决定了用户与插件作者之间的权限关系。VSCode 虽然也支持 multicommands 等定制方式，复杂功能通常仍要通过扩展实现。以打印字数的命令为例，开发者需要学习 TypeScript、创建专门的扩展项目、编写计数函数、注册命令、在扩展 manifest 中声明 contributes，再打包或发布并导入扩展。这样的流程适合专业开发者制作完整产品供他人安装，却让普通用户添加一点个人功能也要承担较高成本。Neovim 的插件则无法获得个人配置所没有的能力；即使某些 API 主要面向插件开发者，它们仍有文档，也向普通用户开放。于是，VSCode 形成"扩展作者生产、用户消费"的双层体系，Vim 则让用户始终拥有自行扩展系统的完整入口。

拥有更多控制权并不自动意味着更好的选择。Wayne 花了很长时间才熟悉基本的 Vim 脚本，即使已经能够自行修改编辑器，要获得现代开发体验，仍然需要依赖他人的插件；他不会为了摆脱依赖，从头编写自己的 Tree-sitter 集成。选择 Vim 因而既要承担学习和维护成本，也无法消除消费他人成果的需要。

VSCode 的优势在于把这种消费过程做得更统一、更可管理。扩展采用一致的安装、设置和使用机制，用户无需每装一个插件就花十分钟阅读配置文档；新增命令、快捷键和配置项可以集中查看，设置界面提供全局搜索与输入校验。用户能够直接启停扩展，也能只在特定 workspace 中启用，而无需修改启动脚本。快捷键发生冲突时，VSCode 会提示，避免旧映射被静默覆盖；其受约束的扩展机制还减少了个人启动脚本、其他插件与编辑器启动过程之间相互破坏的机会。

这些便利与限制来自同一个设计选择：扩展系统更重、更不灵活，配置主要通过静态 JSON 声明，编辑器才能提前识别配置项、校验输入并管理冲突。Neovim 允许配置执行任意程序，想完整判断一个扩展究竟暴露哪些配置选项，就会遇到近似 Halting Problem 的分析困难。这里体现的是 **ability-guarantee tradeoff**：系统允许执行的行为越广泛，就越难对行为结果提供统一保证；限制扩展能力，则为一致性、可检查性和可靠性留下空间。

因此，Wayne 建议大多数开发者保留消费型编辑器，只有确实强烈需要控制权时，再选择 Vim 这类工具。他也把自己的偏好视为一个尚未解决的问题：软件中存在一点无法调整的不合心意之处，就会持续令他难受；这种反应可能更多来自性格，而非衡量生产力后的结果。如果这种不适消失，他是否仍会偏爱 Neovim，自己也没有答案。

Helix 提供了第三种选择：同时限制个人定制与插件消费。它允许接入 LSP server 和 Tree-sitter grammar，却不支持其他类型的插件，静态配置语言也很有限，连针对不同 filetype 设置不同快捷键都做不到。尽管这些限制让 Wayne 难以接受，他仍因长期对 Kakoune 风格的 modal editing 感兴趣，将 Helix 作为当前的主要终端编辑器。他尚未决定是否长期使用，也预料自己最终可能重新渴望可编程的环境；眼下，这至少让他能先熟悉 Nix，再处理数千行 Neovim 配置的迁移。编辑器选择的核心权衡，是用户愿意为多少自主权承担多少复杂性，以及哪些限制能换来自己真正需要的保证。
