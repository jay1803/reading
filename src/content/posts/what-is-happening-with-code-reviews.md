AI 生成代码的速度已经超过人工逐行审查的承载能力，code review 的核心决策正在转向：哪些变更值得人看，以及用什么机制承接其余变更的风险。GitHub 的数据显示，三年间新建 PR 数量增长到原来的五倍；从 2025 年底开始，PR 和 commit 数量又接近翻倍。面对同时增加的 PR 数量与规模，团队开始组合使用 AI 审查、风险分流、前置规格和自动化测试，但尚未形成适用于所有公司的统一流程。

目前最普遍的做法，是让 AI 先审代码，再由工程师**审查 AI 的审查结果**。团队可以接入 CodeRabbit、Greptile、GitHub Copilot Code Review、Claude Code Review 等工具，也可以自建多模型、多 agent 流程；Anthropic 旗下 Bun 项目的 PR 就同时接受 CodeRabbit、GitHub Code Review 和 Claude Code Review 的评论。进一步的自动化会让 agent 根据评论修改代码，再触发下一轮审查。Weaviate 联合创始人兼 CTO Etienne Dilocker 将人的职责集中在两个节点：对抗式 agent 提出问题后，由人决定哪些属于本次变更的范围；agent 完成修改后，由人决定继续迭代还是结束。他认为，完全交给 agent 容易造成范围不断膨胀，或放过严重问题，但逐行人工审查所有代码也无法持续，因此可以把约九成工作交给 agent，将范围与退出条件留给人判断。

这一模式的瓶颈是 AI 评论的噪声：如果工程师需要反复甄别低价值建议，自动审查就会制造额外工作。Series C 旅游科技公司 WeTravel 因此没有采用 AI code review；其在 2026 年 6 月重新评估时发现工具已有明显改善，但收益仍不足以支持采用。Uber 的自建工具 uReview 则把过滤做成流水线：先生成大量评论，再对评论评分、剔除低置信度内容，随后合并、分类并删除不重要的建议，最后只向工程师展示重要问题。AI 能发现多少问题，与它最终占用多少人工注意力，是两个需要分别优化的指标。

另一种分配注意力的方法，是按变更的 **blast radius** 决定是否必须人工审查。OpenAI 和 Anthropic 都采用风险分流：低风险变更主要由 AI 审查，高风险变更必须经过人。Anthropic 的 Jarred Sumner 表示，目前即使低风险变更也仍由人执行合并，但目标是让另一个 Claude 实例接管这一步。因此，"不做人工代码审查"和"完全无人参与发布"仍有明确区别。Uber 也通过自建的 Code Review Inbox 突出显示高影响变更，帮助工程师把审查时间投入后果更严重的地方。

五人规模的云与 AI 成本管理公司 Duckbill Group，提供了更具体的风险分流案例。团队一度积压 60 个 PR，估计需要连续两天才能审完，于是规定：涉及公共 API/MCP、认证、design system、非纯新增的数据库 schema 变更或 agent skills，必须人工审查，并通过 shell 脚本添加 GitHub 标签来执行规则。与此同时，团队加强单元测试、端到端测试、部署后可观测性、lint 和类型检查，几乎启用了 ruff、prettier、eslint、ty 的所有规则，并把单元测试覆盖率下限提高到 85%。这项调整把一部分质量控制工作转移到了自动化护栏和部署后的反馈机制上，代价是额外的 token 与工程注意力投入。

Duckbill Group 公布的前后对比显示，合并 PR 数量从 353 增至 684，每周从 80 增至 154，增幅为 94%；一小时内合并的比例从 28% 升至 45%，24 小时内合并的比例从 76% 升至 80%。需要人工审查的 PR，合并耗时中位数为 26 小时，无需人工审查的为 1 小时。这些数据说明风险分流可以显著缓解审查队列，但没有提供缺陷率或生产事故变化，无法据此判断质量是否同步改善。

还有团队把审查重心移到实现前后的可验证对象：事前审计划，事后审测试与产品行为。更详细的规格可以提前暴露需求歧义和关键决策，Matt Pocock 的 /grill-me skill 就用于通过持续追问完善计划；Musixmatch Principal Engineer Andrea Francesco Speziale 的做法是，宁可花三小时接受追问，也希望实现随后一次完成，不再投入代码审查时间。测试侧则可以采用 TDD，让 agent 先写测试，或重点审查测试是否真正约束了预期行为。这种思路依据的是用户关心软件表现，但其边界同样明确：自动化测试擅长验证业务逻辑，对 UI 是否好看、交互是否舒服的判断能力有限。

Sigil 联合创始人兼 CEO、前 Square 工程师 Jackie Luo 将这一思路进一步收敛到**数据库 schema**。对于快速迭代的创业公司，代码和无状态业务逻辑都容易重新生成，持久化数据却最难恢复和改变；schema 既是已构建产品的硬性表示，也能集中暴露风险最大的决策，因此值得优先投入人工注意力。团队应在调用 coding agent 前对齐产品行为，实现后再借助抽象理解其他重大决定，而对 schema 保持直接审查。这个取舍尤其适合寻找 product-market fit 的阶段；一旦已有稳定业务和用户，业务逻辑就需要测试保护，否则容易修改的代码同样容易破坏用户依赖的行为。

围绕取消人工 code review 的讨论，已经超过实际全面取消它的证据；目前可见的实践主要来自 AI 创业公司，而且通常伴随额外的安全发布机制。减少 agent 生成的代码量、要求更小的 PR，以及继续人工审查全部代码，也仍是团队采用的选择。贯穿这些路径的共同问题，是如何让有限的人工判断覆盖最难逆转、影响最大的错误：AI 降低了生成和重写实现的成本，却让规格、测试、持久化状态与发布护栏的可靠性变得更加关键。
