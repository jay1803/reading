使用今天的 AI agent，最重要的是交代目标背后的原因和优先级，让模型据此判断方案与取舍。早期 agent 需要精确到"class B 已有 method A，请给 classes C 到 F 添加对应方法"的指令，否则就会偏离任务；如今前沿模型做错事，常见原因已转为对用户目标的错误假设。例如，GPT-6-Astra 认为代码只供自己使用时，会生成压缩代码；明确告诉它代码需要由人阅读，它就能写出可读的实现。作者用它生成过数千行可接受的 Golang 代码，说明这种差异来自对使用场景的判断。

作者为 Deckard 项目提供的起始提示，重点就在于让 agent 理解完整的目标和约束：长期希望开发本地程序或浏览器扩展，自动扫描浏览中的网页并隐藏 AI 内容；短期则要找出适合在 MacBook 上运行的 AI 检测模型，以及最高效的运行方式，避免耗电和发热。他提出 Pangram 的 EditLens 3B 与更小的 Roberta 作为候选，同时说明模型可能需要量化和运行优化，并授权 agent 使用 Runpod 做不适合在本机执行的高负载、长时间实验。如果 MCP 无法访问 Runpod，agent 应报告问题；如果发现更好的实现路径，也应提出并与他讨论。

这段提示约有一半用于说明项目背景、个人用途和保持笔记本低温等优先事项，因此模型有空间重新评估用户预设的技术路线。作者认为，如果一开始就把方案写成明确的技术规格，会错过后来发现的改进，包括通过 native messaging 连接本地模型，以及用 Gradient 替代 EditLens。候选模型和实验平台构成了探索的起点，最终选择仍应服务于本地检测的实际需求。

同样的方法也适用于工作场景，但需要更明确地表达技术价值的**相对优先级**。避免 bug、可观测性、与现有代码的协调程度和性能，都可以成为要求；仅仅宣称它们全部重要，无法指导冲突时的决策。作者会明确说明哪些方面可以让步，以换取自己更在意的结果，让 agent 能在具体实现中作出符合预期的权衡。

模型已经能够对更广泛的目标提供有意义的意见，只交给它一份具体技术规格，会重演 **XY problem**：用户已经选定解决手段，却在寻求专家帮助时隐去了真正要解决的问题。充分交代目的、约束与取舍顺序，才能让 agent 同时检验"怎样实现这个方案"和"这个方案是否值得实现"。
