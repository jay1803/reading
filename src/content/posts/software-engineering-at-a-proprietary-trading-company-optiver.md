Optiver 展示了一种由交易盈亏直接塑造的软件工程体系：公司没有外部客户，软件本身就是竞争产品，工程决策必须同时追求纳秒级速度、模型优势和足以避免灾难性损失的安全边界。这里的工程师薪酬可与 Big Tech 顶端岗位持平，原因在于微小的技术领先能直接转化为利润，而一个失控的缺陷也可能摧毁整家公司；Knight Capital 在 2012 年因高频交易系统故障损失 4.4 亿美元、险些破产,至今仍是行业的风险警示。Optiver 因此形成了一种看似矛盾却高度一致的文化：业务要求极快迭代，但生产系统必须经过严谨测试、风险隔离和实时监控。

从资本来源看，Optiver 属于使用自有资金交易的 **proprietary trading firm**，与替外部投资者管理资金并收取费用的 hedge fund，以及为客户提供融资、研究和交易执行服务的 investment bank 不同。它同时扮演 market maker 和 high-frequency trader：持续向交易所提交买卖报价，通过价差提供流动性，并利用自动化策略捕捉短暂的市场变化。基本交易循环每天运行数百万次，包括接收价格或订单簿变化、判断信息意味着什么，以及抢在竞争者之前把订单发给交易所；最快系统进入亚纳秒范围后，测量噪声本身都成了工程难题，软件、定制芯片、Linux kernel、光纤、微波和短波通信必须作为一个整体优化。

交易行业经历了四轮淘汰。1990 年代以前，交易主要在场内和电话中完成；1990 年代早中期，行情搬上屏幕，但订单仍由人手动输入；从 1990 年代末到约 2015 年，计算机开始把人的机械操作自动化并扩大规模；2015 年以后，竞争中心转向由数据、机器学习和推理计算驱动的 quantitative trading。进入这一阶段后，仅靠低延迟已经很难构成持续壁垒，主流机构的执行速度逐渐逼近共同下限，Optiver 如今在改进预测模型上的投入显著高于继续压缩延迟。新的系统形态既包括运行较慢、分析更丰富、再由快速触发器执行的模型，也包括部署在网络边缘、实时作出交易决策的高速模型。

这种竞争不断提高行业门槛。研究计算集群需要数亿美元投入，能够长期参与竞争的大型机构只剩少数。Optiver 于 1986 年在 European Options Exchange 起家，2026 年满 40 年；公司约有 2,200 名员工，其中约 950 名工程师，另有约 1,000 名交易员和研究人员，分布在 Amsterdam、Chicago、Austin、New York、London、Sydney、Shanghai、Hong Kong、Singapore、Taipei 和 Mumbai 等 11 个办公室。它每天在约 100 家交易所执行超过 1,000 万笔交易，2025 年交易收入为 45 亿欧元、利润为 17 亿欧元。如此直接的技术变现能力也让 NVIDIA、Groq 和 Cerebras 积极争取交易机构采购 GPU；Hudson River Trading 已公开讨论 Blackwell 部署，Jump Trading 也成为 Vera Rubin 系统的早期采用者。

量化交易仍建立在数学、机器学习和市场知识的结合上。Optiver 的核心业务之一是期权交易，定价涉及 Black-Scholes 等数学模型，因此参与策略开发的交易员、quant 和工程师都需要理解相关数学。机器学习的重要性持续上升，但它并未取代传统定价理论和市场机制。与此同时，Anthropic、OpenAI 等 AI labs 开始从 prop shop 招募人才，因为这些公司积累了大型自建数据中心、co-location 设施、定制高性能硬件和超低延迟 kernel stack 的经验；顶尖 prop shop 又长期以市场最高水平薪酬吸引优秀计算机毕业生，使其人才结构与 AI 基础设施需求高度重合。

Optiver 的工程组织正在从区域自治转向全球平台。1986 至 2020 年间，各地团队奉行 "unblock yourself"，为本地市场独立建设系统、framework 和 infrastructure；这种模式减少了跨区域依赖，却逐渐造成同一核心逻辑被重复实现、技术栈碎片化以及维护成本上升。约从 2023 年开始，公司加速建设面向全球的统一平台，2025 年任命首位 global CTO Lance Braunstein，并把曾任欧洲 CTO 的 Pat Cooney 调任 platform engineering 负责人。CI 也从多套区域服务重建为可跨地区运行、能长期扩展的统一系统，使一个地点构建的软件可以在其他地区顺畅部署。

平台投入因此远高于普通科技公司：Optiver 约 30%—40% 的 950 名工程师从事平台工作，而大型科技公司的常见比例约为 15%—20%。过去，新工程师可能花数周才能完成代码 checkout 并让构建系统正常运行；现在平台团队强调用户同理心，为开发者配置构建流水线并消除开发路径中的摩擦。随着 coding agent 普及，平台的用户也扩展到自动化系统，公司已经建设统一的 **AI gateway** 供工程师访问模型，以及 MCP hosting platform，让 agent 能安全接入内部系统和工具。其目标是让员工把复杂工作拆成多个 workstream，再由人编排 agents 执行。

公司的技术岗位主要分为 engineering、research 和 trading，但角色边界有意保持开放。研究人员通常来自数学、物理、经济学和统计学，负责提出假设、建立模型和预测信号；交易员观察实时市场、调整参数并作出风险决策；工程师负责生产系统。实际项目通常由三类人员共同完成，研究员可能直接实现策略，工程师也可能参与研究。生成式 AI 又进一步降低了交易员和 quant 编写生产工具、自动化工作流与实现策略的门槛，使这种角色融合加速。

交易团队通常按资产类别和策略组织，例如 options、ETF 与股票等 cash market，以及面向 cash market 的 ML 策略。较大的组织内部同时存在 horizontal team 和 vertical team：horizontal team 处理定价、市场连接和自动交易等跨交易台问题，时间跨度较长；vertical team 围绕某个地区若干交易台的当前高价值问题快速行动，但仍是长期存在并具备端到端责任的团队。每个团队通常由 trading 或 research lead 与 tech lead 共同确定工作，整体战略则由一组 senior partners 制定，partners 并不必然直接管理团队。

无论组织形态如何，所有交易系统都围绕同一闭环展开：获取市场信息，汇总信号，执行策略，再由交易员或自动化机制监控并干预。工程师从问题定义开始参与，随后负责设计、实现、测试、部署和生产监控，不存在把质量责任移交给独立 QA 团队的做法；公司每天会进行数百次生产变更。涉及架构调整时，项目负责人需要提出多个方案及其利弊，通过 design review 共享知识并形成决策。新员工和实习生从第一天就获得真实项目和明确所有权，在导师支持下提交生产代码，并被期待在一年内成为该领域能够指导下一位新人的专家；面试也会专门考察问题拆解、权衡分析和落地能力。

期权业务中的 **retreat system** 体现了这种端到端优化。每完成一笔期权交易，市场状态就发生变化，Optiver 必须重新计算与之相关的整个 option surface；在 S&P options 中，这可能意味着同时更新数千个期权。旧报价若没有及时撤销，速度更快的对手就能利用 stale price 获利。十年前一次 retreat 需要数秒，如今通过跨软件、硬件和网络层的连续优化已缩短到纳秒级。这类对抗性约束解释了为什么低延迟策略有时会把多个步骤放进同一块 FPGA 或 ASIC：系统预先计算所有预期输入对应的策略响应，再将结果固化进硬件，尽量缩短市场信息抵达和订单发出之间的路径。

逻辑上，交易软件可分为 signals、strategy 和 execution 三层。signal 服务收集行情、价格和订单簿数据，并运行定价算法与机器学习 pipeline；多个并发 strategy 服务据此决定交易对象和方式，但不直接发送订单。所有策略都被一个具有全局视野的风险系统包围，它可以阻止订单或关闭单个策略，并通过交易员调整参数及自动化边界检查共同控制风险。对于反应窗口短于人类操作速度的策略，系统必须实时判断订单输出是否落在预期范围内。execution 层则严格执行 separation of concerns，只负责把已批准的交易发送到交易所，避免在最关键、最难审计的路径中混入额外决策逻辑。

这些应用运行在多层内部平台之上。基础设施层包含 Kubernetes、Kafka、Postgres 和 CI/CD 等常见组件，同时加入自建数据中心、定制硬件、定制 Linux kernel、数据库改造和专用 CI 工具；domain-specific infrastructure 则提供证券 metadata、交易数据字典和 trade booking system 等行业能力。Optiver 通常选择成熟的行业标准工具，再针对可预测性能和极端延迟要求进行深度改造，而全球平台团队正在把历史上散落于各办公室的重复实现逐步整合起来。

语言选择同样服从工作负载：C++ 承担低延迟应用，Python 用于建模、原型和内部工具，Rust 开始进入研究工具与服务编排，C# 用于数据密集型交易员 GUI，VHDL 和 SystemVerilog 用于 FPGA。Python 在这里也承担严肃的性能任务，Optiver 维护了高性能 Postgres 异步库 optiver-asyncpg、能细粒度控制间接依赖的 vulcan-py，以及自动化和模拟网络设备的 opti-napalm。Rust 当前更多用于增强 Python 相关工具，没有大规模替换 C++，因为公司数十年积累的低延迟 C++ 生态已与定制硬件深度结合，并允许精确控制内存分配等底层行为。

CI/CD 必须在装有定制硬件、操作系统经过特殊调优且性能曲线可预测的 bare-metal machines 上运行，因此测试集群也要像生产系统一样提前规划容量；AI coding tools 提高了每位工程师每天触发构建的次数，使这一问题更加紧迫。Optiver 选择 GitHub Actions 以获得与 GitHub 一体化的开发体验，但 Actions 缺少跨系统的 queue time 和 utilization 指标，公司于是通过 GitHub webhooks 自建观测层来支持容量决策。数据平台以 Databricks 为中心，并大量使用 Kafka 和 Postgres；公司为 Postgres 贡献了支持纳秒精度的 timestamp9，还基于 write-ahead log 构建内部 "PG Feed"，用于向大量客户端低延迟分发定价和配置数据，避免 Kafka 额外的磁盘读写。

Optiver 的真正技术壁垒由一整套相互约束的系统构成：硬件和网络把反应时间压到物理极限，模型决定在速度趋同后谁能更准确地理解市场，统一平台降低全球工程组织的协作成本，而强所有权与独立风险控制确保高频迭代不会把局部错误放大成公司级灾难。
