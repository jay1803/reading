URI 的持久性取决于维护者能否让资源标识独立于持续变化的技术和组织安排，并长期兑现同一个地址可用的承诺。Tim Berners-Lee 在这篇 1998 年的文章中指出，域名所有者原则上控制着域名及其下全部 URI，除非组织倒闭或无力维持服务，网站就有条件保留既有地址。大量失效链接来自地址设计欠缺远见，以及维护者把网站改版、文件搬迁、人员交接和软件替换当成了更换 URI 的理由。

这些变化大多可以在地址背后完成。Apache 等服务器允许 URI 与实际文件位置之间建立灵活映射，因此文件换了目录，公开地址仍可保留；John 把维护工作交给 Jane，也不应影响文档标识，这恰好说明最初把 John 的个人目录写进地址埋下了隐患。对于材料过多、无法分辨哪些过期或涉密而索性关闭整个档案库的问题，W3C 曾有亲身经历：公开历史资料之前必须逐份检查保密要求。解决办法是在文档创建时保存允许的传播范围、创建日期，最好还有失效日期，让日后的访问与归档决策有据可依。

把服务器实现机制写进 URI，会让软件升级直接变成链接危机。National Science Foundation 的文档入口 `/cgi-bin/pubsys/browser/odbrowse.pl` 暴露了脚本目录和 Perl 扩展名，报告索引 `/cgi-bin/getpub?nsf9814` 也依赖当时的程序接口；同一报告正文的 `/pubs/1998/nsf9814/nsf9814.htm` 则更有延续性。即使到了 2098 年文档编号制度已经改变，`pubs/1998` 仍能让档案维护者明确识别这套历史分类。它保留的是文档产生时的背景，减少了对当前软件实现的依赖。

期待 URN 自动解决持久性问题，同样回避了维护责任。许多 URN 方案由权威机构标识、日期和自选字符串组成，与 HTTP URI 的构成并无根本差异；一个组织若有能力维持长期有效的 URN，就可以立即用相同原则分配 HTTP URI，再通过数据库把标识映射到当前文件名。HTTP 本身并不迫使地址失效，标识与存储之间的映射能否持续维护，才决定链接能活多久。

工具不足却是一个真实障碍。理想的系统应能即时解析持久 URI，无论文件目前存在哪里；把 URI 保存在文件内以便核对，持续校准映射数据库，记录不同版本及译本的关系，并独立保存 checksum 来发现意外损坏。文档的所有权、访问范围、归档级别和安全级别都应能够改变，同时保留原 URI。写作当时的服务器尚未普遍提供这些能力，W3C 使用基于 Jigsaw 的 Jigedit 跟踪版本，并试验文档创建脚本，自己的不少页面也未完全达到文中要求。要让持久地址成为常态，编辑器和服务器必须共同支持这种工作方式。

维护者承担这项责任，是因为他们永远无法完整知道旧地址被引用在何处。链接可能出现在别人的网页、浏览器书签，甚至写给朋友的信件页边，站内改版无法同步修复这些分散的引用。访问者遭遇断链时，既无法完成原本的任务，也会降低对网站维护者的信任。附录中的 Channel 7 案例还显示，失效可以比 404 更隐蔽：1999 年提供雪天停课信息的 `/stormforce/closings.shtml`，到 2000 年第一场大雪时仍显示"目前没有停课"，却缺少日期；网站首页指向的新地址 `/stormforce/` 实际列出了大量停课学校。Microsoft Netmeeting 客户端内置的"Help/Microsoft on the Web/Free stuff"链接返回 404，则说明厂商更换地址还会破坏已经发布的软件功能。

因此，设计 URI 的核心工作是**删去会变化的信息**，并以能够维持两年、二十年乃至两百年为目标。作者姓名会随交接或版本变化，`draft`、`old` 等状态会随文档生命周期变化，访问权限也会从内部讨论转为公开发布；W3C 原先把 Team、Member 和 Public 访问范围分开编码，就面临每次扩大讨论范围都可能破坏旧链接的问题。`.html`、`.cgi`、`.pl`、`exec` 乃至磁盘名称，则把格式、程序或物理存储写成了公开承诺。创建日期，也就是分配 URI 的日期，一经确定便不会变化，还能区分新旧命名体系，因此适合作为地址前缀，例如 W3C 的会议纪要地址 `/1998/12/01/chairs`。

有意表示"最新内容"的页面需要单独理解。Money 杂志的 `/money/moneydaily/latest/` 标识的是持续更新的最新栏目，这一概念依赖杂志继续出版；要引用某一天的具体内容，则应使用归档地址，例如 `/money/moneydaily/1998/981212.moneyonline.html`。后者虽然有重复的年份和可省去的 `.html`，仍然清楚地固定了一份历史内容。持续更新的入口与某次发布的内容具有不同身份，稳定地址应分别对应这两种资源。

主题分类尤其容易让地址设计失去长期稳定性，因为它在当下往往显得十分合理。W3C 曾希望把 `MarkUp` 改成 `Markup`，再改成更符合内容的 `HTML`，也很快遇到想重新使用 `History`、`Stylesheets` 等名称的情况。更深层的困难在于，主题之间呈网状关系，不同人即使认可相同的知识关联，也会选择不同的树状分类；一旦把主题层级写进 URI，就把资源绑定到了某一种分类方案。按部门或工作组划分地址空间，也会把组织结构的变化带进链接。若确实需要保留主题或组织名称，可在前面加上日期：`1998/pics` 固定的是"1998 年所说的 pics"，从而避免要求未来始终沿用同一含义。

同样的约束也适用于域名和子域名。`cgi.pathfinder.com`、`secure`、`lists.w3.org` 这类名称把软件机制、安全安排或服务划分暴露给外部，一旦后台重新组织，已有链接就可能受损；多个实际服务器可以通过代理和重定向呈现为一个统一站点，无须让公开地址复制内部部署结构。主域名也需要考虑业务变化：用 `soap.com` 命名，就要承担未来转做其他产品后仍保留这一名称的后果。

在实现层面，去掉 URI 扩展名并不要求删除实际文件的扩展名。Apache 的 content negotiation 可以让 `/mydog` 对应同一目录下的 `mydog.png`、`mydog.gif` 等表示形式，并选择合适的格式；已有的带扩展名链接仍能使用，但会固定到特定格式，失去协商选择当前或未来格式的能力。`mydog`、`mydog.png` 和 `mydog.gif` 都可以是有效资源，只是前者不限定内容类型。数据库映射也能把持久标识与当前表示形式分离，但需要承担当映射不断积累时的维护成本。持久 URI 的根本价值，是让文件、格式、权限、人员和服务器都能演变，同时把外界已经建立的引用关系保留下来。
