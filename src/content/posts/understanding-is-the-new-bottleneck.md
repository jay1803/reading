## 理解是为了参与，而不是为了核验

Agent 越来越能自我验证代码正确性，这让"理解是为了检查对错"的理由越来越站不住脚。作者的核心主张：你需要理解，因为一个项目由无数轮人机循环构成，你脑中对系统的概念地图直接决定你能提出什么样的下一步想法。没有这种概念流畅性，你参与创作的能力被实质性截断。类比于技术债——不理解短期没事，但迟早会封顶你的创造力上限（Margaret Storey 等人称之为"认知债"）。

## 三种加速理解的技术

### 1. 解释：把 diff 变成教材

=/explain-diff= 技能：每次 agent 完工后生成结构化 HTML/Markdown 解释器。结构是：先讲背景知识（change 之前系统是什么），再给直觉铺垫（原理先于代码），最后是"散文化 diff"——按逻辑顺序而非文件字母表顺序讲解改动，还可以嵌入交互式图形。解释器底部附带五道测验题，规定在自己通过测验前不把代码发给别人。测验是"速度调节器"：它机械地强迫确认是否真的理解，而不是漂过去了。

### 2. 微型世界：住进系统，而非站在系统外

灵感来自 Seymour Papert 的"Mathland"——想学法语就住到法国去。实践逻辑：用 agent 构建能让自己亲手操作的环境，不是让 agent 代替你操作。两个例子：一是为自己的 Prolog 解释器做了可拖时间轴的可视化调试器，自己逐步执行逻辑；二是框架迁移时，Claude 做了一个"指挥中心"游戏，让作者点按钮一步步完成迁移，同时看两套网站并排演化——获得了"近似手写"的理解深度，但耗时只是其中一小部分。关键元级别洞见：**agent 可以写"帮助人类理解其他代码"的代码**，这是一个新的使用模式。

### 3. 共享空间：团队层面的共同心智模型

单人理解不够。两人共享同一套概念地图，交流才能高效，才能快速"jam"出新想法；没有共享结构，这类创造性对话要困难得多。作者的方向：让 agent 在协作文档（Notion）里做技术计划，团队成员可以直接在同一页面评论，而不是各自在 silo 里跑自己的 agent。

## 底线

Alan Kay 50 年前的愿景就是用计算机增强人类思维，而非替代。AI 让构建模拟世界和教学环境变得容易，这是计算史上少有的机会——让我们比以往任何时候都能更深地理解世界。选择权在人类这边：是退出循环，还是更深地参与循环。
