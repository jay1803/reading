## TL;DR
这篇文章最有价值的地方，不是再讲一遍“agent 很火”，而是把 agent 重新定义成一个**架构分层问题**：先判断你是在自动化一个已知流程、让模型自主决定动作序列，还是在协调多个专门代理。很多团队之所以 prioritization 失真，不是不会排优先级，而是把本质上不同的系统放进同一张 impact-effort 表里比较。

## 核心主张拆解
**分类先于 roadmap 排序**
作者认为，所谓 agent backlog 之所以常常越排越乱，是因为同样叫“agent”的东西，建设周期、团队配置、运行成本、成功指标都完全不同。一个项目可能 6 周上线、月成本几百美元；另一个可能要 6 个月、需要专门的 ML 工程团队、还会带来六位数年度模型账单。先分型，后排序，才有可能讨论 ROI。

**Category 1 = Deterministic automation，绝大多数团队该从这里起步**
这类系统的本质是：流程由人预定义，LLM 只在若干节点做理解、抽取、生成。判断标准不是“有没有 AI”，而是流程能不能被画成有限分支的流程图，通常分支少于 15–20 个、完成时长在秒到分钟、价值来自自动化一个已知流程而不是探索新路径。作者给出的经验判断是，60%–70% 的 agent 机会其实都属于这一层。

**Category 1 的核心收益，不是炫技，而是快速 ROI**
对应工具是 n8n、Zapier、Make、OpenAI AgentKit 一类工作流系统。评估指标也高度工程化：完成率、自动化率、准确率、延迟、单次工作流成本、错误率、人工复核率。文章给的客服邮件自动化案例，从第 1 周 52% 完成率提升到第 8 周 87%，最后每月自动化 3000 封邮件、每天释放 2.5 个 FTE 小时、月节省约 1.8 万美元。这里真正的判断框架是：先拿低风险、可量化、短周期的问题建立组织信心。

**什么时候该从 Category 1 升到 Category 2**
如果你的流程图已经膨胀到 30+ 节点、分支每周都在加、用户表达方式无法预先穷举、系统必须根据上下文自己决定调用哪个 API 或知识源，那它就不再适合工作流范式。也就是说，升级的触发条件不是“我们也想做更酷的 agent”，而是 deterministic workflow 已经无法承载问题复杂度。

**Category 2 = Reasoning and acting，价值在动态决策，不在固定流程**
这类系统的关键不是工具更多，而是**同一个高层任务每次可能走不同动作序列**。你定义工具集，LLM 决定下一步做什么，典型形态是 observe → reason → act → observe result 的循环。适用场景包括多工具协同、上下文驱动的选择、含糊意图澄清、多模态输入理解，以及把复杂任务拆成子任务本身就是产品价值的一部分。

**Category 2 的代价更高，所以必须用更像产品经营的指标看它**
文章给出的评估口径包括任务完成率、推理准确率、对话长度、多模态准确率、工具调用效率、延迟、单 session 成本、CSAT 和业务提升。案例里，一个家居零售商的语音+图片购物助手，从 Month 1 的 71% completion / $0.12 单次成本，优化到 Month 4 的 86% / $0.08，同时图片识别准确率从 76% 提升到 91%，转化 lift 从 +8% 提升到 +22%。这说明 Category 2 不是“更智能就行”，而是要证明动态推理带来的收益大于额外复杂度和成本。

## 反驳或薄弱处
公开可读内容在 Category 3 刚开头时被 paywall 截断，所以当前能确认的是前两类架构、升级信号与对应指标体系；多代理网络部分的完整展开、适用边界和评估框架并未读到，不能替作者补全。换句话说，这篇文章已经足够支撑“先分层、再排序”的方法论，但对 Category 3 的判断仍只拿到了引子。

## 最后一笔
作者真正想纠正的不是 agent 定义，而是组织做 AI 项目时的默认决策顺序。多数团队的问题，不是缺少 agent 想法，而是太早把“更自主、更复杂”误当成“更先进”。这篇文章的隐含建议其实很朴素：先用 Category 1 把确定性流程吃干抹净，再把少数确实需要开放式决策的问题交给 Category 2，至于 multi-agent，应该是组织复杂度已经逼出来的结果，而不是 roadmap 上最先拿来讲故事的招牌。
