## 嘉宾背景

Jeremy Epling，Vanta CPO（统管产品、设计与工程三条线）。职业轨迹：微软 20 年（Windows、Internet Explorer、OneDrive），后以 GitHub 产品负责人身份深度参与微软收购 GitHub，在 Nat Friedman 创始人文化下主导 GitHub Actions 从 0 到 GA（9 个月交付）。2024 年加入 Vanta，这是他的第一个 CPO 职位。

## TL;DR

Jeremy 认为 CPO 最危险的失误不是战略错误，而是 **从细节里抽身** ——一旦你变成"专业管理者"，产品质量判断就会空洞化；而速度的真正瓶颈不是人手不足，而是组织对新成员的 **吸收容量** 已经先于人头增长触顶。

## 在细节里才能设质量标

Jeremy 明确站在"founder mode"一侧：CPO 必须亲自用产品、留 Figma 注释、参与深潜会议——不是微观管理，而是保持"感知通道"。他的论据：当大公司形成"专业管理层 + 做活儿的人"两层结构时，产品方向感最先消失，因为顶层已经不知道产品实际长什么样。

他的实践：每天早晨 2-3 小时 IC 时间（走查产品、跑 bug、写文档、留反馈），每周 deep dive 让产品团队带着原型走进来演示。进 Figma 留评论是常规动作，但他也在学一件事：**区分"这是想法"和"我要求你执行"**——否则高管扩音效应会让团队把每条评论都当作命令执行。

## CPO 的第一团队是 C-Suite，不是 EPD

升到 CPO 之后最难的切换不是技能，而是视角：你的"第一团队"从工程/产品/设计变成了整个 C-suite。Jeremy 说朋友们提前警告他这个陷阱，他几乎还是掉进去了——因为 EPD 就是他的"快乐地带"。

CPO 在 C-suite 的核心贡献是**把客户视角带进跨职能决策**——他花在客户电话上的时间通常超过其他 C-level，这是他最有价值的信息优势。反过来，他要把这个信号用 C-suite 能消化的方式（更高海拔、更短文档）喂给其他人。

## 产品 vs. 营收的结构性张力靠关系，不靠制度

产品团队（长期导向、薪酬以底薪+期权为主）和营收团队（月/季度 quota、极度短期）从激励机制上就是对立的。Jeremy 没有给出"解决方案"，而是说：**这种张力本身是有价值的**，你要做的是管理它，不是消除它。

管理方式：CPO 和 CRO 一对一高频对齐；带着"这是一个问题"而非"你应该做这三件事"进 C-suite 讨论；让产品团队分享他们从客户那里观察到的信号，和销售团队的信号做比对，建立"共享真相"。他最讨厌的模式：产品团队成为"接单方"，销售说什么修什么，战略就此消失。

## 吸收容量是增长期真正的速度限制

Vanta EPD 每季度增加约 50 名工程师，但 Jeremy 认为真正限制交付节奏的不是人数，而是 **absorption capacity**（团队对新人的吸收容量）。每块代码库的吸收容量不同：新代码库可以快速接收新人；旧的、乱的代码库容量极低，硬加人只会更慢。

他的量化指标：每个 squad（8-10 工程师 + 1 PM + 1 设计师）每月统计时间分配——新功能 / 架构重写 / 保持灯亮 各占多少；日期达成率期望 90%，低于 80% 才开始担心；每个 ramped 工程师的 feature announcement 产出作为长期效率指标。工程师入职第一周就要合并 PR 进生产环境。

## 留下的那个想法

Jensen 的"不要一对一"在 NVIDIA 有效，是因为整个组织是围绕那套系统选拔和驯化的——把它直接移植到自己公司是危险的。Jeremy 的观点是：**你无法把一个生态系统里进化出来的管理实践孤立地复制出去**，文化实践和组织规模之间存在适配关系，借鉴前先问"我们的人签约加入的是什么样的系统"。
