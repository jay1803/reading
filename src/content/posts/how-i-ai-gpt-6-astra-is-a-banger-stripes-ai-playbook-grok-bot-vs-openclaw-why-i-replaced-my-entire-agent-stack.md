Claire 把整套 OpenClaw agent 迁到 Grok Bot，直接原因是维护成本已经抵消了工具带来的便利。她能配置 Tailscale、通过 SSH 连接 Mac Mini，甚至专门建立了管理其他 bot 的救援 bot，但仍然难以让 OpenClaw 长期稳定运作。Grok Bot 提供相近的能力，同时更容易配置、能可靠保持在线，这就足以促成全面迁移。对横跨多个业务的她来说，多账户支持尤其重要：六个 Gmail 账户、多个 Slack 和 Linear 工作区可以同时连接，并交给同一个 agent 处理，省去了在彼此隔离的账户环境之间反复切换的成本。

她用“招聘新员工”的方式设计 agent，为每个 bot 指定名字、职位和职责边界，避免一个助手逐渐变成没有重点的通才。这些专职 bot 分别承担邮件管理、家庭协调、pull request 审查、SOC 2 合规、客户支持、订阅审计和买衣服等任务。家庭助手 TradBot 的成功标准甚至是减少与它互动的时间：它把家庭定制报纸打印出来，放在早餐桌旁，也能把摘要发送到 Kindle，让信息进入已有的生活习惯，无须再增加一套盯屏幕的流程。

明确职责之后，还要划清自主执行与人工批准的边界。客户支持 agent Holly Helpdesk 可以处理退款流程，但真正退款前必须请求 Claire 批准；通知中的按钮会打开实际的 Stripe 请求，她核对并确认后才执行。上线一周内，Holly 已经收到客户主动给出的五星评价。SOC 2 agent Lockdown 则登录控制面板、检查问题、调查新增漏洞，并在通知她之前提交包含修复方案的 pull request，把人工介入集中到审核变更的环节。两者共同体现的原则是：低风险工作自主推进，有实质后果的动作保留审批，同时尽量让 agent 完成调查和修复，减少交给人的待办事项。

Grok Bot 仍然需要针对表达和主动性进行配置。Claire 发现它默认把文字压缩得过度，句子容易破碎，于是让它研究自己发出的邮件、建立详细的个人语气档案，之后才允许它处理低风险的对外沟通。OpenClaw 的 heartbeat 会让 agent 自然表现得更主动，Grok Bot 则需要显式创建 routines 才会定期行动；代价是用户必须逐项决定何时触发，收益是所有周期任务都能在设置中清楚查看和审计。迁移时，她先让 Lifeguard 导出不含密钥的归档，保存每个 agent 的身份、定时任务和 gateway 配置，再把文件夹上传到 Grok Bot，恢复原有个性、上下文和职责。保留回退所需的信息，让更换平台不必伴随失去长期积累的风险。

Stripe 的经验把同一问题扩展到了企业规模：模型接入之后，最难的工作是让 agent 理解组织边界，并在合适的权限与系统负载下运行。Engineering manager Sharadh Krishnamurthy 与同事以约 1.5 名工程师的投入，用两周做出内部 agent Kai 的首个版本；如今每周使用者超过一万人，采用率达 86%，维护团队仍不足十人。这种规模依赖 Stripe 多年积累的内部基础设施，以及辅助平台开发的 coding agents，不能简单归因于小团队接上了一个强模型。

Kai 的 **projects** 是团队级配置层，能由少数熟悉业务的人统一选择默认模型、批准可用工具、规定哪些操作需要人工审核，其他员工直接继承适合其工作的设置。HR project 使用独立的安全后端和严格受限的工具，防止敏感员工数据进入公开文档。员工面对的是一个统一产品，无须自行判断连接器、模型和数据权限的组合；安全规则预先嵌入正常使用路径，也就减少了员工因合规流程太慢而绕开它们的诱因。

这套治理还必须延伸到基础设施。Stripe 已有分层分析目录、具备韧性的 Trino 查询引擎和可信指标层，原本服务人类开发者的投资，成为 agent 大规模可靠查询数据的基础。即便如此，agent 仍曾以异常行为和请求量冲击核心系统，几乎拖垮生产环境。更好的提示词不足以解决这些问题，Stripe 必须加入 agent 专属身份、请求优先级信号、负载丢弃机制，以及能够承受新增需求的查询层。Sharadh 因此建议，在大举投资 agent 之前，先把 developer experience 和数据团队的规模翻倍：agent 会放大既有系统的薄弱环节，使原本可控的问题迅速演变成容量与可靠性风险。

Kai 通过可复用的 **skills** 把一次成功对话转化为持续可用的组织能力。员工可以保存工作方法，为其填写触发条件和面向 Kai 的执行规范，并在编辑器内测试后发布；系统会自动选择合适的 skill，使用者只需描述需求。目前 Stripe 约有两千个 skills，其中约五十个每天在公司内使用。库的扩大也会引入无关检索上下文，降低结果质量，因此团队用遥测区分全公司常用技能、小团队依赖的高价值流程，以及数周无人使用的内容，再决定推广、合并或淘汰。使用频率只是判断依据之一，维护技能库还要避免误删服务少数人的关键工作流。

GPT-6 Astra 的测试则显示，模型能力的跃升会改变人愿意尝试的项目。Claire 曾为 ChatPRD 的一项 product intelligence 功能卡了六个月：她无法在提示词里充分解释整个系统，早先模型因此反复做出不合适的架构决策。Astra 首次尝试便完成约九成，经过几轮跟进收尾。她还报告，自己如今约九成工作时间可以不碰键盘；在 Adio 的可视化工作流编辑器中，Astra 能新增节点、重接逻辑并生成定制的潜在客户回复邮件，而早先模型因操作精度不足，让她放弃过类似尝试。

这种计算机操作能力也让耗时的 QA 更容易交给 agent。Astra 曾连续一小时四十五分钟测试一个开发分支，检查 race conditions 和流式输出的边界情况，查看 console、主动刷新应用，并持续寻找故障。它的价值包含对重复测试的耐心，尤其适合人类容易匆忙略过的环节。Claire 由此重新判断“no UI is the next UI”的前提：当 agent 能可靠操作复杂视觉界面，产品团队就不必为了机器访问而把一切都改造成 API 或命令行，按钮和图形界面仍然可以保留其表达产品逻辑的优势。

更高的能力上限还体现在硬件、3D 和定制工具上。面对没有公开 API 的 Divoom Mini 2，Claire 此前花了数月仍进展有限，Astra 则逆向解析其像素算法，建立实时传输的命令行工具，让节目资料与图片可以直接显示到设备上。它还通过单次提示，在 Blender 中构建了可玩的 Barbie 风格换装游戏，为家庭应用创建了孩子可以走进图书馆、到池塘记录情绪的 3D 世界，并一次生成围绕真实 Codex threads 运作的复古 AIM 桌面界面，包含输入状态和 away messages。这些用途使高度个人化、难以证明值得投入传统开发团队的软件，开始具有实际可行性。

生产环境中的另一项进展是延续已有设计。设计师不在时，Astra 能进入 Flora 和 Figma，研究既有流程与视觉风格，制作符合品牌审美的缩略图，让生成结果直接接入现成工作体系。不过，Claire 给出的价格是每百万 input tokens 10 美元、每百万 output tokens 50 美元，长时间计算机操作和 QA 尤其需要考虑输出成本。她主张把它用于长期卡住的开发问题、复杂视觉界面和高重复劳动测试，让额外能力对应足够高的任务价值。贯穿这些案例的共同门槛，是把模型能力与具体职责、可靠运行、权限边界和既有系统连接起来；只有这些环节同时成立，AI 才能从偶尔惊艳的演示变成可以持续交付结果的工作系统。
