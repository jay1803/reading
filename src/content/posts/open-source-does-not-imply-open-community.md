## TL;DR
GitHub 把“发布源码”默认改造成“运营社区”，结果是个人维护者被迫承担产品经理、客服、仲裁者和组织管理员的职责；真正的选择权在于：开源只要求代码可被使用、阅读、修改和再分发，并不要求项目向陌生人开放治理入口。

## 核心主张拆解
- 早期开源可以很轻：一个 HTML 页面、txt 说明、FTP tarball、邮件地址，最多再加 mailing list 或非官方 IRC；源码开放成立，但没有社区运营包袱。
- SourceForge 到 GitHub 的演进降低了公开协作成本，也改变了默认期待：issue、PR、wiki、roadmap、核心团队、行为准则和讨论区逐渐被当成“正常开源项目”的标配。
- 作者认为这个默认期待把维护者拖进无薪组织劳动：下班后继续处理工单、需求变更、架构性 PR、投诉、聊天群冲突和陌生人的情绪管理。
- 对个人项目而言，社区化常常把“我做喜欢的软件”变成“我经营一个半技术孵化器、半托儿所的空间”，维护者失去范围控制和方向感。
- 大型复杂项目确实可能需要团队和治理机制，但作者强调那是例外；多数项目不应被 GitHub 平台范式自动升级成公共机构。

## 可执行的边界选择
- 关闭 issue tracker 和 pull requests，让仓库回到发布渠道，而非协作入口。
- 使用 bare git server 或其他更窄的发布方式，只把代码 drop 出来，不承诺处理外部请求。
- 只与少数真正认识、信任的人合作，或者完全独立开发。
- 不为陌生人额外制定表演性的 Code of Conduct、LLM policy 或治理文本，除非项目规模和目标真的需要。
- 使用任何自己想用的工具，在任何时间发布；开源许可不等于要把个人创作空间改造成公共服务台。

## 值得质疑
- 文章把“社区”主要描绘成维护者负担，弱化了社区对 bug 发现、移植、文档、生态扩散和长期可持续性的正面价值。
- 它没有区分“拒绝无边界协作”与“完全缺少贡献路径”的后果：后者可能让项目更自由，也可能让软件在作者离开后迅速失活。
- 对 Code of Conduct 的批评偏情绪化；在多人协作场景中，最低限度的行为边界未必是表演，也可能是降低冲突成本的基础设施。

## 最后一层意思
这篇文章最有价值的提醒是：开源维护者可以把“源码开放”和“治理开放”拆开设计；真正稀缺的不是更多协作入口，而是维护者对注意力、边界和项目意图的主权。
